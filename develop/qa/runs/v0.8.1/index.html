    Finding Type Action
    write_doc_content clear+reinsert leaks stale font_size/font_family into new content (reproduced 4×) Real bug Filed as #255; fixed in PR #258, then corrected in follow-up PR #259 — see note below
    TC-DOC57's SVG test image URL rejected by live Google Docs API Test-file fix Fixed in docs/qa/tests/docs.md (this branch, TC-DOC57/58)

    Decision: both real bugs were folded into v0.8.1 rather than deferred (user's call) — fixed on dedicated branches (PR #257, #258), each verified beyond the mocked unit-test layer (#254 is pure local logic, fully covered by a unit test; #255 touches live Docs API behavior, so it was verified directly against the API before merging, consistent with this project's "unit tests mock the API, they can't catch integration drift" testing philosophy).

    #258's first fix was wrong despite passing its own live verification — corrected by #259. #258 combined the clear (updateTextStyle + deleteContentRange) and the new content's insertText into one batchUpdate call; a single live check happened to pass. After both #257 and #258 were merged, re-verifying live against develop (post-merge) surfaced that the combined-batch approach is unreliable: the Docs API appears to resolve a same-batch insertText's inherited formatting from a pre-batch snapshot, so contamination could still leak through depending on document state, even though the clear request ran earlier in the same batch. Isolating each step and repeating the full cycle multiple times (not just once) showed the fix only holds when the insert is sent as its own separate, subsequent batchUpdate call. This is exactly the kind of integration drift a single live check can miss and unit tests can't catch at all — the lesson being applied going forward: verify a live API-behavior fix by repeating the full cycle several times, not just once, since a single pass can pass by luck of document state.
