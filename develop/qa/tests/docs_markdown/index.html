    Docs — Markdown Rendering — QA Test Cases¶

    Source: every write path that turns a user's Markdown into a Google Doc. That's our converter (tools/docs/content.py _md_to_html → html_parser.py → emitter.py), Drive's native Markdown import (tools/drive/transfer.py _CONVERT_MIME[".md"]), and Drive's HTML import of upload_file(source_format='markdown').

    Tracking: #1044. This file is the v0.9.4 release gate for Markdown rendering: v0.9.4 ships when every case below passes on screen through every entry point.

    Fixtures: docs/qa/fixtures/md/. The nesting, containment, adjacency, inline-matrix, long-document and docstart/ fixtures, and the four matrix tables in this file, are generated by uv run python scripts/qa_gen_md_fixtures.py (--check reports drift); change those there, not by hand. Substitute {FOLDER_ID} (a throwaway child folder of TEST_FOLDER_ID, see "Running this suite") and {REPO} (absolute path of the checkout the server under test runs from).

    Rules¶

    1. Playwright is the oracle. Every case is Playwright: required. The verdict comes from the rendered Doc on screen, with one screenshot saved per case per entry point. get_doc_structure and get_doc_as_markdown are supporting evidence only, never the verdict: the Markdown export writes every numbered item as 1., so it can't see a numbering restart, and it may be blind to more. "Confirmed via unit tests" or "known gap, visual only" is not a result.
    2. The expected rendering is written down before a case runs (this file). It says what a reader sees: numbering, indent level, glyph, font, link target. Where the screen alone can't settle a detail, the case names the structural check that does (the Structural column or line).
    3. A known failure is a FAIL. "Matches documented failure mode," "known gap," "pre-existing," and "not a new regression" are never a PASS. A failing case stays FAIL, linked to an open issue, until the fix lands and the case passes on screen.
    4. Nondeterminism is a FAIL. The whole matrix runs twice (Run 1, Run 2). A case that renders differently across the two runs fails, even if both renderings look acceptable.
    5. No sampling. Every case goes through every entry point in the table below, unless the case is marked N/A for an entry point with a reason. Shared code is how a path-specific wrapper bug hides.
    6. Anything that looks wrong is a finding, whether or not a case below covers it. Phase 1 especially: read each document top to bottom against its source.

    Entry points¶

    Every case runs through every entry point. EP-1 to EP-4 use our converter. EP-5 to EP-7 use Drive's native Markdown import (they upload the .md file and Drive converts it). EP-8 converts with Python-Markdown's extra extension and then uses Drive's HTML import. A rendering difference between engines is itself a finding: the same Markdown should read the same way whichever tool turned it into a Doc.

    EP Tool call (fixture F = absolute path of the .md file) Engine
    EP-1 create_doc(title="MD-<case>-EP1", content=<contents of F>, content_format="markdown", folder_id="{FOLDER_ID}") ours
    EP-2 write_doc_content(doc_id=<a blank Doc in {FOLDER_ID}>, content=<contents of F>, content_format="markdown") ours
    EP-3 create_doc_from_file(local_path=F, title="MD-<case>-EP3", folder_id="{FOLDER_ID}") ours
    EP-4 update_doc_from_file(doc_id=<a blank Doc in {FOLDER_ID}>, local_path=F) ours
    EP-5 upload_local_file(local_path=F, parent_folder_id=<empty child of {FOLDER_ID} for EP-5>, convert=True) Drive Markdown import
    EP-6 upload_local_folder(local_path=<a temp dir holding only F>, parent_folder_id=<empty child of {FOLDER_ID} for EP-6>, convert=True) Drive Markdown import
    EP-7 sync_folder(local_path=<a temp dir holding only F>, folder_id=<empty child of {FOLDER_ID} for EP-7>, direction="upload", convert_markdown=True) Drive Markdown import
    EP-8 upload_file(name="<case>.md", content=<contents of F>, source_format="markdown", folder_id="{FOLDER_ID}", convert_to_doc=True) Python-Markdown extra + Drive HTML import

    EP-5, EP-6 and EP-7 each get their own empty child folder: these tools skip a file whose converted Doc already exists in the target folder (skip_if_exists defaults to True), so a shared folder would turn a later entry point's render into a skipped.

    Not an entry point: no tool inserts Markdown at an index in an existing Doc (insert_doc_text takes plain text). The "insert at an index" state in #1044 is therefore N/A; if such a tool is added, it joins this table.

    Parameter variants that only some entry points take:

    • autolink_urls=False (EP-1 to EP-4 only; the Drive engines have no such switch): run md-links.md a second time with it. Cases LK-05 and LK-06 then expect plain, unlinked text; every other links case is unchanged.
    • Images with a local path or drive: source (IM-04 to IM-06): EP-5 to EP-8 don't resolve them, so those cells expect whatever Drive does with an unresolvable image reference. Record what's on screen; a broken-image icon or literal ![...](...) text is a FAIL for that engine.

    What correct looks like in a Google Doc¶

    Markdown describes HTML, and Docs has no direct equivalent for some constructs. These conventions turn "renders correctly" into something checkable. They follow the converter's documented design (docs/design/markdown-support.md, docs/design/blockquote-representation.md) where one exists.

    # Construct Expected on screen Structural check when the screen is ambiguous
    C1 ATX/Setext heading level N Docs "Heading N" style (font size and weight of that named style) get_doc_structure: namedStyleType == HEADING_N
    C2 Bullet list, levels 0/1/2 Glyphs ● / ○ / ■, each level indented one step further bullet.nestingLevel = 0/1/2; contiguous same-type items of one Markdown list share one listId (a bullet run nested in a numbered list is its own Docs list)
    C3 Numbered list, levels 0/1/2 1. 2. … / a. b. … / i. ii. …; numbering never restarts inside one Markdown list, including after a nested block contiguous same-type items share one listId; the screen is the verdict for the number shown, since a nested block of the other type is a separate Docs list
    C4 Task item Bullet item whose text starts with ☐ (unchecked) or ☑ (checked); no literal [ ]/[x] —
    C5 Inline code Courier New on exactly the code characters textStyle.weightedFontFamily.fontFamily == "Courier New" on that run only
    C6 Code block (fenced or indented) One Courier New block; each source line on its own visual line; leading indentation and blank lines kept; no Markdown inside it interpreted one paragraph (lines joined by soft breaks), all runs Courier New
    C7 Blockquote, depth N Indented N steps with a gray left border; content inside keeps its own formatting (lists stay lists, headings stay headings) paragraphStyle.indentStart = 36pt × N and borderLeft set
    C8 Thematic break A visible horizontal line across the page; never an empty-looking gap —
    C9 Hard break (two trailing spaces, \) Line break inside the same paragraph: no extra blank line, no paragraph spacing between the two lines one paragraph containing a \v (soft line break)
    C10 Soft break (a plain newline inside a paragraph) The lines join into one paragraph, separated by a space one paragraph
    C11 Image The image itself is visible at its natural size (or scaled to page width); alt text is not shown as visible text inlineObjectElement present
    C12 Link Link-styled text (blue, underlined) whose target is the Markdown URL hover or textStyle.link.url
    C13 Table A Docs table, header row bold, cell text and inline formatting intact; column alignment from :--/:-:/--: applied to the cells of that column tableCells[].content[].paragraph.paragraphStyle.alignment
    C14 Block inside a list item (paragraph, code, quote, table, heading) Shown under the item, indented to the item's text, not as a new top-level block and not as literal Markdown; the list continues after it (next item keeps the list's numbering and nesting) the screen is the verdict: the next item shows the continued number or glyph; it shares the preceding items' listId when they're the same type
    C15 Empty paragraph spacing No visible empty paragraph that the source doesn't imply. The known collapsed blank paragraph before each table (docs/known-limitations.md, "Blank paragraph before every table") must stay invisible —

    Decisions where CommonMark/GFM and what a user means disagree, approved by the maintainer on 2026-10-17. Each is the expected behavior for this plan; changing one changes the expected rendering of the cases that cite it.

    • D1 — nesting width. A list marker indented at least 2 spaces (or one tab) further than the previous item's marker nests under that item, whatever the parent's marker width. CommonMark requires the child to reach the parent's content column, so 1. A followed by - a1 (2 spaces) doesn't nest under CommonMark, but that is how models and people write sub-bullets, and #1044's own example expects it to nest.
    • D2 — a table starts its own block. A pipe table directly under a paragraph, list item or quote line (no blank line) renders as a separate table after that block, not as text joined to it.
    • D3 — YAML front matter is not shown. A leading ----delimited YAML block is omitted from the Doc (docs/design/markdown-support.md currently calls it "acceptable" that it renders as a rule; that is a FAIL under this plan).

    Anything CommonMark/GFM permits that the converter deliberately won't support goes into docs/known-limitations.md, tied to an open issue, and its cases stay FAIL until a decision changes the expected rendering here.

    Running this suite¶

    1. Server and slot. Use a server running the code under test with LOCAL_FILE_ACCESS=full (EP-3 to EP-7 are local-only tools). Use an OAuth identity, or a service account with a Shared Drive {FOLDER_ID}.
    2. Throwaway folder. Create a child folder of TEST_FOLDER_ID named QA-MD-<date>-run<N> and use it as {FOLDER_ID}. Everything this suite creates goes there. Trash the folder after the results are recorded.
    3. Placeholders. md-images.md contains {QA_IMAGE_LOCAL_PATH} and {QA_IMAGE_DRIVE_ID}. Copy the fixture to docs/qa/fixtures/md/syntax/md-images.local.md (next to the original, so IM-05's relative path still resolves the same way), substitute the absolute path of docs/qa/fixtures/qa-fixture-pixel.png and the Drive ID of an uploaded copy of it, and use the copy. *.local.md under docs/qa/fixtures/ is ignored by version control, so the substituted copy (it holds a resource ID) can't be committed by accident.
    4. One render per fixture per entry point. Each syntax fixture holds many small cases, each under its own ### <ID> — <description> heading, so one render covers them all and a failure still points at one construct. Phase 1 documents and the document-boundary files (docstart/) are one case per file.
    5. Screenshots. Open the Doc at https://docs.google.com/document/d/<id>/edit and take one screenshot per case, scrolled so the case's heading and its full content are in view. Name it docs/qa/screenshots/md/<run>/<EP>/<case>.png (the screenshots/ tree is gitignored; keep the files until every issue filed from the run has them attached). Follow the Playwright mutex in run.md §"Coordinating Playwright across parallel shards", and verify the account first per §"Verifying Playwright is signed into the right account".
    6. Order. Phase 1 first, and file its failures before starting Phase 2 (#1044, "obvious problems first"). Then Phase 2, then the document-state cases.
    7. Determinism. Repeat the whole matrix as Run 2 in a fresh folder. Compare each case's Run 2 screenshot with Run 1.
    8. Recording. Write the per-case × per-entry-point grid to docs/qa/results/<date>-markdown.md (rows: case IDs; columns: EP-1 to EP-8; cells ✅, ❌ with the issue number, or N/A with the reason). Under each TC below, add one summary line: **Result (<date>) ❌ FAIL — <passed>/<total> case×EP cells pass; failures: #…**. A TC is ✅ PASS only when every cell of every case in it passes in both runs.
    9. Group. docs/qa/operations.yaml run_group with group: docs_markdown runs this file.
