Branch naming for this slot always puts `<name>` as the **second** `/`-separated segment — `<type>/<name>/issue-<n>` — where `<type>` is whatever this repo's existing convention calls for given the ticket's nature (`feat`, `fix`, `chore`, `docs`, ...; see recent branch names for precedent). **One ticket per session — refuse a second one.** Once this session has created or committed to a ticket branch (`<type>/<name>/issue-<n>`), it never starts a different ticket, even when the user tells it to. A session can't clear itself. Why: every turn re-reads the full context, so a ticket started on top of a finished one pays for that carried context on every turn (measured in #843).

Once told, then:

Keep `--no-track`: without it the ticket branch's upstream is `origin/develop`, so a bare `git pull` merges `develop` in and a push under a non-default `push.default` can land WIP on `develop`. Push with `git push -u origin <branch>` at step 6 to set the right upstream.
  2. Work through the issue fully — code, tests, doc changes:
     - When adding a tool to a file whose siblings share a parameter (e.g. every `sheet`-taking tool in `structure.py` calls `_get_sheet_id` and returns a clean `{"error": ...}` for a bad name), grep for that shared pattern across *every* sibling in the file, not just the one or two you used as a reference (PR #361).
     - Before converting a sequential loop to `asyncio.gather` fan-out, audit it for order-dependent assumptions, such as an existence/dedup check computed once against a pre-batch snapshot. Don't just port the body into a gather (PR #351: two same-named Drive files raced to one local path).
     - Scope is every problem the issue body and its triage comments describe, not just the one its "Suggested fix" covers (PR #877). To leave out anything the issue describes, ask the user before opening the PR. A note in the PR body doesn't count as asking.
  3. Run the test suite.
  4. Run `/prep-for-pr`.
  5. If the ticket added `TC-DOC`/`TC-D`-style entries to a shared `docs/qa/tests/*.md` file, confirm before pushing that the IDs are still free. These files are append-only and shared by both lanes, and an open PR can reserve IDs long before it merges (PR #829 collided with open #830).

Use `sort -V`, not `sort -n`, which falls back to text order on a `TC-` prefix. The `^### ` anchor matches definitions only, not cross-references.
     - On every open PR touching the file: `gh pr list --state open --json number,headRefName,files --jq '.[] | select(any(.files[]; .path == "<test-file>")) | "\(.number) \(.headRefName)"'`, then for each branch `git fetch origin <branch> && git show origin/<branch>:<test-file> | grep -oE "^### <PREFIX>[0-9]+" | sort -V | tail -1`.

Full playbook: `.claude/team-roles/aziz.md`'s "Ad-hoc deep-dive QA" section.

Fix anything inside this diff in this PR. Open the PR first. ## Retro

Friction Dev (Ash/Jay) typically hits after finishing a ticket, and where it goes — see `/retro` for the general ticket-vs-command-decision split. Each entry is the rule; the incident behind it is in [`role-file-history.md`](../../docs/decisions/role-file-history.md#devmd).

- **Design/architecture surprises** — an existing pattern didn't generalize the way expected mid-implementation (a sibling function skipped a step this one needed, a helper needed restructuring to fit a new case). If it's about how future Devs should approach similar work, that's a command decision: add a note to `CLAUDE.md` or a `docs/design/` snapshot, through the Bob gate above. If it's legitimate follow-up scope not worth doing in the current PR, it goes through step 6's follow-up triage, not straight to a ticket.
- **Take the generalized fix when QA's send-back names a root cause** (e.g. "X is a scalar, not a stack"), not just a symptom list, even when it's more work than patching the listed cases. A narrower patch leaves the same defect class reachable one level up and costs another QA round (PR #369 took three).
- **Verify QA's suggested code against the actual invariant before adopting it; a correct diagnosis can come with a wrong fix.** When a change touches a state flag that gates several conditions (`_tag_depth`, `_table_depth`, `_block_tag`, or equivalents), grep every read-site of the flag and compare the conditions by hand before opening the PR. Running the suite isn't enough (PR #406).
- **Scope creep discovered while implementing** — related, unshipped bugs or gaps adjacent to the ticket but not part of its acceptance criteria. Don't fold them into the current PR; triage them through step 6's follow-up rule, which files a ticket only under a named bar.
- **Stale or missing `CLAUDE.md` guidance** for a pattern you just hit: fix `CLAUDE.md`, through the Bob gate above, not a direct push.
- **QA-authoring ambiguity** — writing test cases in `docs/qa/tests/` surfaced an unclear tagging rule or fixture assumption in `run.md`/`setup.md`. Command decision: clarify the doc rather than guessing silently and leaving the next Dev to guess the same thing.
- **Special-casing a category means the whole category.** When new state-tracking logic must special-case "elements with property X," audit against the complete formal set, not the instances the surrounding code already mentions (PR #385 excluded `<br>` but not the other HTML5 void elements). Likewise, before shipping logic that relies on a property holding across an open input category (charsets, codecs, MIME types, locales), check every member, e.g. every `codecs.lookup()` name in `encodings.aliases`. Pair random-input probes with adversarial inputs, and gate on an explicit allowlist rather than whatever a probe happened to pass (PR #829).
- **Before any retro commit, check that this PR hasn't merged under you.** Run `git log --oneline -3`. If the ticket's merge commit is already an ancestor, cherry-pick your commit onto a fresh branch cut from current `origin/develop`, per `merge-pr.md`'s stray-commit rescue, instead of committing on the stale branch: a plain push can resurrect the deleted branch name (PR #353). An empty cherry-pick means the content already landed another way: delete the stray branch (`git branch -D`, and `git push origin --delete <name>` if pushed) and reset this worktree to `team/<name>`. With more than one scratch-branch checkout in flight, re-run `git branch --show-current` right before every `git add`/`git commit`: another session can switch this worktree's branch mid-edit with no error (#363, PR #368).
- **`uv lock` rewriting markers on packages you didn't touch means your local `uv` differs from the one that wrote the lock** (PR #877). Don't commit that. Re-lock with the current release without changing the installed one: `uvx --from uv@latest uv lock`. That may bump the lockfile's `revision =` header (3 → 5 with 0.12.23, checked 2026-10-04); that's expected, and older `uv` still reads it. Only marker changes on unrelated packages are the problem. If that isn't possible, revert `uv.lock`, add only the project's own lines (its `dependencies` and `requires-dist` entries) by hand, and confirm with `uv lock --check`.
- **A docstring's "same mechanism as X" isn't proof the paths share a fix.** When a fix adds a marker, flag, or stamped property so one code path recognizes an artifact, grep for every function whose docstring or comments claim equivalence and verify each one (PR #414).
- **Recognizing an artifact this tool already created must depend on the artifact's own persisted state, never on the current call's creation flag.** Only creating a *new* one should require the flag (PR #414: a resync that omitted `convert_markdown=True` duplicated the Doc).
