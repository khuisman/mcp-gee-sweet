QA role (Sky / Kit). Reached via `/team-member <name>` after that command's shared isolate + tool-boundary steps.

Find the partner Dev's open PR by matching the branch's second `/`-separated segment against the partner's lowercase name — not a `feat/`-specific prefix, since the Dev's branch type varies: `gh pr list --state open --json number,headRefName,url --jq '[.[] | select((.headRefName | split("/"))[1] == "<partner>")]'`. At most one is expected, since a lane only has one ticket in flight at a time.

- **None found:** self-heal first — `git fetch origin develop`. If this worktree's `HEAD` isn't already `origin/develop`, `git reset --hard origin/develop`: since the partner has no open PR right now, any leftover commits here are a stale copy of a PR this lane previously reviewed (now merged or closed) — this worktree never holds original work of its own, only reset-in copies of a Dev's PR branch, so it's always safe to discard. Then report that Lane {A/B} has nothing to verify right now.
- **One found:** this is now essentially `/verify-pr`'s steps 4 onward, but simpler — this worktree already IS a dedicated review space, so skip `/verify-pr`'s steps 1–3 (the main-checkout precondition and the `review/<branch>` fetch trick don't apply here):
  1. `git fetch origin <headRefName> && git reset --hard origin/<headRefName>` in this worktree, staying on `team/<name>` (never create a branch named after the PR here — this slot's identity is `team/<name>`, permanently).
  2. Tell the user to run `/mcp reconnect` (standalone, on its own line) so this agent's own MCP connection picks up the reset code. Wait for confirmation.
  3. Run `/code-review` at `high` effort against `origin/develop...HEAD`.
  4. Scope and run the live QA steps from `/verify-pr` (its steps 6–8: find touched `docs/qa/tests/` cases, cross-check tool coverage, run them live using this worktree's own `mcp-gee-sweet-<name>`-prefixed tools).
  5. Record `**Result**` entries for every case actually run.
  6. If anything failed: push the recorded results (`git push origin HEAD:<headRefName>`, with confirmation), comment on the PR summarizing what failed, and stop — tell the user it goes back to the Dev agent.
  7. If everything passed: push the results, then `gh pr edit <number> --add-label qa-approved`, and report to the user that it's ready for Kai to run `/merge-pr`.

## Retro

Friction QA (Sky/Kit) typically hits after a pass, and where it goes — see `/retro` for the general ticket-vs-command-decision split:

- **Fixture drift/pollution** — the shared spreadsheet/doc accumulates stray objects (charts, temp sheets/rows, leftover permissions) from earlier test runs, breaking `docs/qa/setup.md`'s "Known fixture state" assumptions or blocking visual verification. If a specific test category is the source (e.g. a creation test with no teardown), file a `qa`-labeled ticket against that category rather than just working around it silently. If it's a workaround you need *right now* to finish this pass, that's a command decision — document it in `docs/qa/run.md`'s Playwright-limitations list so the next pass doesn't rediscover it (see the "Chart-covered grid" entry, added 2026-07-15, for the pattern).
- **Playwright verification gaps** — an element is structurally unreachable or invisible to the browser tools (outside the viewport, canvas-rendered with no accessible geometry, obscured by other content). Command decision: add it to `run.md`'s limitations list along with whatever alternative verification actually worked (e.g. `get_sheet_data(..., include_grid_data=True)`'s `rowMetadata`/`columnMetadata` for pixel-precise dimension checks, when a screenshot can't show it).
- **Test tag drift** — `⚠️ requires-oauth` or `**Playwright: required**` no longer matches a test case's actual behavior. Small, obvious ones: fix the tag directly in the test file (command decision, mechanical). Larger or systemic drift: don't duplicate #264 (the tracked tag-consistency audit) — add to it instead.
- **QA test-doc setup steps that don't match tool behavior** — e.g. a `**Setup:**` line telling you to use a tool that doesn't actually do what the step assumes (a "replace" tool cited where an "append" was meant). Fix the test-case text directly in `docs/qa/tests/*.md` as part of the same pass (command decision), not a ticket — it's QA process content, not product code.
- **Code-review findings that are minor or systemic rather than PR-blocking** — input-validation gaps, duplicated helpers, style inconsistencies that the new code merely repeats from an existing convention rather than introduces. These are tickets (`enhancement`/`backlog`, or `defect` only if a failure was actually observed), not reasons to withhold `qa-approved` — don't hold one PR hostage to fix a codebase-wide convention. See #323 for the shape this takes (validation + dedup findings from the same review, bundled into one issue since they shared a root cause); see #329 for a comments-API-scoped example of the same pattern.
- **Live-observed API quirks that aren't bugs** — e.g. a field the docstring implies is always populated but the live API omits for privacy/scope reasons on certain paths. Note it inline in the test case's `**Result**` entry (so the next run isn't surprised), but don't file a ticket unless the tool's own docstring is factually wrong about the contract — that's a documentation-label ticket instead.
- **Lane/partner misidentification** — presenting the user a choice between PRs, or reviewing a PR, before confirming its branch's second segment actually matches this role's partner (this file's own `jq select` query above). If this happens, the fix is a command decision in this file or `verify-pr.md` (tighten the wording so the partner-match check runs *before* any PR is surfaced to the user), not a ticket — it's a process-following gap, not a product one.
- **CI rollup false positives** — `statusCheckRollup` can omit a required check entirely (absent, not failing) while other checks (e.g. CodeQL) populate normally, which reads as "all green" if you only scan for failures. Command decision → `merge-pr.md` step 2 (already tightened once, 2026-07-16 — re-tighten if a new variant of this shows up rather than re-discovering it).
- **Coverage gaps in the PR itself** (a changed tool with no QA test case at all) are not a retro item — that blocks the pass and is handled inline per this file's step 4 / `verify-pr.md` step 6, not deferred here.
