Cut a stable release: merge `develop` → `main`, tag, publish to PyPI via a GitHub Release, then merge `main` back into `develop` so subsequent dev builds immediately pick up the new version as their base. Run this from the main checkout, on `develop`, clean.

**Precondition — release QA sign-off.** This command executes a release, it doesn't decide whether one is ready. Confirm Aziz's release-QA pass has landed on `develop`: a `docs/qa/runs/vX.Y.Z.md` sign-off (and matching `docs/qa/results/<date>.md`) for the version being cut. If it's missing, stop and tell the user to run the release QA pass first (`/team-member Aziz`) — don't review or test anything yourself here. A hotfix's scoped sign-off ("Hotfix from the last tag" below) can arrive by message instead: quote it in a comment on the hotfix PR before merging.

**Precondition — get the approvals up front, in the user's own words.** In auto mode the classifier can refuse this command's outward steps unless the user's own words in this session cover them, and allow rules don't override it. In v0.9.4 it refused a branch-protection edit and even a read-only `gh release view` of an earlier release. Before step 1, ask once for an approval that names each step: merging to `main`, tagging and publishing (the GitHub Release fires the PyPI upload), the MCP registry publish, the merge-back to `develop`, and any branch-protection change the release needs. A refused step goes back to the user; never route around it.

**Precondition — refresh the MCP registry login before tagging.** `mcp-publisher`'s token expires, and an expired one only fails at main step 7 (`401: Invalid or expired Registry JWT token`), after PyPI already has the release. Unless this session has already published with it, ask the user to run `! mcp-publisher login github` (an interactive device login) before main step 4.

1. **Determine the version.** Check `docs/roadmap.md`'s Release Cadence table for the target version, and confirm it against the last tag (`git tag --sort=-creatordate | head -1`) so the bump direction (patch/minor/major) makes sense. Confirm the exact version string with the user before proceeding if there's any ambiguity.
   - **Check that every README link and image URL is absolute, now, on `develop`.** `README.md` becomes the PyPI project page, which doesn't resolve repo-relative paths the way GitHub does: a relative image renders broken and a relative link 404s, and a published release's README can't be changed afterward (#706, then #1062: v0.9.2's check covered images only and missed four relative links). Run it here, where a fix is one PR to `develop`; step 4 re-runs it on `main` as the backstop. `<ref>` is `origin/develop` here; run `git fetch origin develop` first:
     `git show <ref>:README.md | python3 -c 'import re,sys; d=sys.stdin.read(); s=re.findall(r"\]\(([^)\s]+)", d)+re.findall(r"\s(?:src|href)=[\"\x27]([^\"\x27]+)[\"\x27]", d)+re.findall(r"(?m)^\s*\[[^\]]+\]:\s*(\S+)", d); bad=[x for x in s if not x.startswith(("https://","http://","mailto:","#"))]; print(len(s), "urls"); sys.exit("not absolute: %s" % bad if bad else 0)'`
     It must exit 0. On a nonzero exit, fix the listed URLs with a PR to `develop` (absolute `https://github.com/<owner>/<repo>/blob/main/...`, or `/tree/main/...` for a directory) before step 2.
2. **Bump the MCP registry manifest (`server.json`) to the new version, before merging to `main`.** `pyproject.toml`'s version is dynamic (`uv-dynamic-versioning`, derived from the git tag) and needs no manual edit — `server.json` is the one file in this repo that does.
   - Branch off `develop` (e.g. `chore/release/server-json-vX.Y.Z`). Set both `version` (top-level) and `packages[].version` in `server.json` to the exact version string from step 1 — they must match each other (`tests/test_server_json.py::test_pypi_package_version_matches_top_level_version` enforces this).
   - Open a PR, wait for every `Lint and test (Python 3.x)` check to pass, merge with `gh pr merge <number> --admin --squash` — `develop` requires 1 approving review a solo maintainer can't get natively, same reason step 3 below uses `--admin` for the `main` merge.
   - `git checkout develop && git pull` so the local checkout has the bump before continuing.
   - This lands *before* the develop→main PR (step 3) so the version bump ships in the same release rather than trailing it.
3. **Merge `develop` → `main`.**
   - Check for an existing PR first (`gh pr list --base main --head develop`); open one if it doesn't exist (`gh pr create --base main --head develop --title "Release vX.Y.Z" --body ...`).
   - Wait for every `Lint and test (Python 3.x)` check (one per Python version in `ci.yml`'s matrix) to pass — do not merge on a failing, pending, or missing one.
   - Merge with `gh pr merge <number> --admin --merge` — a real merge commit, **not** `--squash`. This repo's existing `main` history is a chain of "Merge pull request #NNN from khuisman/develop" merge commits (see `git log origin/main`), not squashed releases; squashing here would collapse that convention. `--admin` is required the same way it is in `/merge-pr`: `main` requires 1 approving review that will never come from a solo maintainer, and `enforce_admins` is `false` specifically so this bypass is allowed — it must never be used to skip the "Lint and test" check itself.
4. **Tag the merge commit.**
   - `git fetch origin main`
   - **Re-run step 1's README check against `origin/main`, before tagging** (`<ref>` = `origin/main`). It must exit 0. On a nonzero exit, stop: don't tag. Report the listed URLs to the user, since fixing them takes a PR to `develop` and a new `develop` → `main` merge.
   - `git tag vX.Y.Z origin/main`
   - `git push origin vX.Y.Z`
5. **Write the release notes, then create the GitHub Release from that tag.** The auto-generated PR list alone isn't release notes: write a short header in a scratch file first, and show it to the user before creating the release.
   - **Title:** `vX.Y.Z — <Name>`, using the version's dinosaur name from its `docs/roadmap.md` section heading (e.g. `v0.9.4 — Ankylosaurus`; naming rules in `kai.md` §"Release scoping"). A hotfix has no name: title it `vX.Y.Z — hotfix`.
   - **The dinosaur:** a synopsis of 3–5 sentences. Say when and where it lived, what it looked like and what it's known for, and one line on why it fits this release's theme. Use only well-established facts: no speculative behavior stated as fact, no contested size figures. Skip this for a hotfix.
   - **What's in it:** the theme and the feature set, a few bullets in user terms with issue links; the fill in one or two lines; then a **Breaking and behavior changes** list (a renamed tool, a changed default, a removed parameter). Write "None" if there are none, never omit the heading.
   - Create it: `gh release create vX.Y.Z --title "vX.Y.Z — <Name>" --notes-file <file> --generate-notes` (target `main`). With both flags, gh prepends your file to the generated PR list. This is what fires `.github/workflows/publish.yml`'s `release` trigger and its `pypi-publish` job. The same file publishes dev builds on pushes to `develop`, so every upload comes from one trusted publisher and PyPI doesn't flag the release with a "Change of provenance" warning (#1124).
6. **Verify the stable PyPI publish.**
   - `gh run list --workflow=publish.yml --event release --limit 1` and watch it to completion. Keep `--event release`: without it the latest run may be a dev build from a push to `develop`.
   - If it fails with `invalid-pending-publisher`: the PyPI trusted-publisher registration reverts to "pending" state once a project already has a publisher on file — tell the user to add `publish.yml` as a *current* publisher on the PyPI project's Publishing page (not re-add as pending), then `gh run rerun <run-id> --failed`.
   - Confirm the new version is actually live (`pip index versions mcp-gee-sweet` or check the PyPI project page) before moving on.
   - Confirm its provenance: the wheel's `attestation_bundles[].publisher.workflow` is `publish.yml` (`curl -s "https://pypi.org/integrity/mcp-gee-sweet/X.Y.Z/<wheel filename>/provenance"`), and the release page shows no "Change of provenance" warning. TC-I66 (`docs/qa/tests/infra.md`) has the full steps. A different workflow there means the upload bypassed `publish.yml`, and a "Change of provenance" warning means PyPI saw a different publisher on the previous upload. Either way, tell the user before continuing.
   - Confirm the MCP Bundle is attached: `gh run list --workflow=mcpb.yml --event release --limit 1` concluded `success`, and `gh release view vX.Y.Z --json assets --jq '.assets[].name'` lists `mcp-gee-sweet-X.Y.Z.mcpb`. The bundle's version comes from the tag, so no file needs a bump for it. A failed run doesn't affect PyPI: tell the user, and don't re-tag. `gh run rerun <run-id> --failed` retries it (the upload uses `--clobber`).
7. **Republish the MCP registry manifest and confirm the new version is discoverable.** `server.json`'s ownership verification fetches the README from the exact PyPI release its `version` points at — run this only after step 6 confirms that release is live, not before.
   - Precondition: `mcp-publisher` CLI installed and authenticated as the `io.github.khuisman` namespace (`mcp-publisher login github` if not already logged in).
   - From the repo root: `mcp-publisher validate server.json` — must report `server.json is valid`.
   - `mcp-publisher publish` — must report `✓ Successfully published`. A failure here almost always means the `mcp-name: io.github.khuisman/mcp-gee-sweet` marker isn't present in the README of the exact PyPI release `server.json`'s `version` points at.
   - `curl "https://registry.modelcontextprotocol.io/v0.1/servers?search=io.github.khuisman/mcp-gee-sweet"` — response must include a server entry with `version` matching `server.json`.
   - This is TC-I29's (`docs/qa/tests/infra.md`) own re-run trigger — full setup/action/checks detail lives there. Run it every stable release that bumps `server.json`'s version, not once-and-done.
8. **Post-release — merge `main` back into `develop`, immediately, every time.** This is the step that was previously skipped and caused real breakage: after v0.8.1 shipped 2026-07-05, `main` never got merged back into `develop`, so `git describe --tags` — which `uv-dynamic-versioning` uses to compute the dev version — kept resolving to the last tag `develop` could already see (`v0.7.0`). Every dev prerelease for the next week+ silently published as `0.7.0.devN` instead of `0.8.1.devN`, even though `develop` had moved well past v0.8.1's feature set. Do not treat this as optional cleanup.
   - `pwd` and `git branch --show-current` first — confirm you're in the main checkout on `develop`, not a stale worker worktree.
   - `git fetch origin main develop`
   - The merge-back is a PR from `main` into `develop`, never a direct push: ruleset 26262344 rejects a direct push to `develop`, since it needs CodeQL results the pushed commit can't have yet (2026-10-31). `gh pr create --base develop --head main --title "Merge main into develop after vX.Y.Z release" --body-file <file>`.
   - It should show no conflicts, since `main` only ever receives commits that originated on `develop`. If it does, stop and investigate rather than resolving them in the PR.
   - Once every check passes (CodeQL included), `gh pr merge <number> --admin --merge`: a merge commit, never `--squash` or `--rebase`, which would copy `main`'s commits instead of merging them, leaving the tag out of `develop`'s history. `--admin` only skips the review gate; nobody else reviews a merge-back.
   - Then `git checkout develop && git pull` in the main checkout.
   - **A hotfix tagged anywhere other than `origin/main`'s tip** ("Hotfix from the last tag" below covers the case where it is `main`'s tip; for any other, agree the procedure with the user first): also merge the tag itself into `develop`, even when the fix already reached `develop` through its own PR. Do it on a branch off `origin/develop` (`git merge vX.Y.Z -m "Merge vX.Y.Z hotfix into develop"`), push the branch, and merge it the same way as the merge-back PR above. If the merge isn't clean, stop and investigate, as above. Without the tag in `develop`'s history, `git describe` keeps resolving to the pre-hotfix tag and every dev build sorts below the hotfix (#317).
9. **Verify version continuity on both branches** — don't just assume step 8 worked:
   - `git describe --tags origin/main` must print exactly `vX.Y.Z` (distance 0). If not, the tag isn't actually on `main`'s tip — stop before publishing or telling the user anything is done.
   - `git describe --tags origin/develop` must show `vX.Y.Z` as its base (e.g. `vX.Y.Z-N-g<hash>`), not an older tag. If it still resolves to a prior tag, the merge-back didn't take (wrong branch, push failed, etc.) — re-check before reporting success.
   - `publish.yml`'s dev track only fires on pushes to `develop` touching `src/**`, `tests/**`, `pyproject.toml`, or `uv.lock` — a no-op merge commit may not trigger it, so don't expect an automatic dev-publish run right after the merge-back. That's fine: the `git describe` check above is what proves the *next* real push will publish under the correct base. Don't force a throwaway push just to watch a workflow run.
10. **Move `next-release` (feature release only; skip for a hotfix).** Remove the label from every ticket of the version that just shipped, open and closed. Those are exactly the tickets carrying it now, since a hotfix never gets it: `gh issue list --label next-release --state all --limit 500 --json number`, then `gh issue edit <n> --remove-label next-release` for each. Apply it to every ticket of the next queued version (the first `planned:` section in `docs/roadmap.md`'s queue order), open and closed: `gh issue list --label "planned: <name>" --state all --limit 500 --json number`, then `gh issue edit <n> --add-label next-release`. If no version is queued, apply it nowhere. Then confirm `gh issue list --label next-release --state all --limit 500 --json number --jq length` matches `gh issue list --label "planned: <name>" --state all --limit 500 --json number --jq length`. Rules: `kai.md` §"Release scoping" rule 3.
11. **Report a summary:** the stable version tagged and confirmed live on PyPI, the release URL, whether the `.mcpb` is attached, the merge-back PR and its merge commit hash, both `git describe` outputs from step 9 as proof the two branches are version-consistent, and confirmation that step 7's registry search returned the new version.

## Hotfix from the last tag

Use this when a fix already merged on `develop` must ship without `develop`'s other unreleased work, and `origin/main`'s tip is the last stable tag (as it is after every `develop` → `main` release). It replaces main steps 2–3; main steps 1 and 4–10 run as usual. "Main step N" below means the numbered list above; a bare "step N" means this section's own list.

1. **Kai cherry-picks; it's not a ticket.** A cherry-pick of commits that were already reviewed on `develop` isn't new authorship: don't file a lane ticket, wake a Dev, or run a QA round for it (maintainer, 2026-10-22). Create the branch in its own worktree off the tag (`git worktree add .claude/worktrees/hotfix -b hotfix/vX.Y.Z <last-tag>`), so the main checkout stays on `develop`. Then `git cherry-pick -x <sha>` for each fix commit, keeping each commit as it was reviewed. If any pick's patch-id differs from its original (step 4), it needs new code: that's a Dev hand-port with a QA round, not this section.
2. **Regenerate the lock on the tag.** A commit from `develop` carries `develop`'s `uv.lock`, which can include unrelated version bumps. Run `uv lock --upgrade-package <pkg>==<version develop's lock pins>` for each package the fix bumps (or a plain `uv lock` if it bumps none), and run `uv lock --check` last, so it checks the final lock. Read each pin back (`grep -A1 '^name = "<pkg>"' uv.lock`) and compare it with `develop`'s entry. Commit any difference as a separate commit, so each cherry-picked commit stays as it was reviewed. Its diff against the tag should touch only the packages the fix meant to change.
   - **A passing `uv lock --check` doesn't prove the fix's packages moved.** When the picked commit carries the lock's own requirement lines for a new floor, uv treats the tag's lock as current and keeps the old pin, which only the fix's own guard test (#1218's) caught (v0.9.5). Hence the explicit `--upgrade-package` and read-back.
3. **Bump `server.json`** in its own commit on the same branch: set both `version` and `packages[].version` to the hotfix version. If the fix's PR added a `## [X.Y.Z] — Unreleased` entry to `CHANGELOG.md`, date it in its own commit before merging (main step 8 then expects a conflict on it).
4. **Open a PR to `main`.** In the body, list each cherry-picked commit with its original, the lock diff, and the fidelity check: for each pair, `git show <original> | git patch-id --stable` and `git show <picked> | git patch-id --stable` print the same first field. A mismatch means the pick changed the reviewed diff: stop, it's a Dev hand-port (step 1).
5. **Aziz signs off with a scoped pass:** live cases for the code paths the fix touches, run against the branch's head, plus green CI. Kai confirms the diff and lock checks from step 4 and tells Aziz they're done, so the pass doesn't repeat them. Quote the sign-off on the PR, then merge with `gh pr merge <number> --admin --merge` (a merge commit, as in main step 3) and continue at main step 4. The release title is `vX.Y.Z — hotfix`.

Two main steps behave differently for a hotfix:

- **Main step 7 runs from the hotfix worktree, not the main checkout.** The main checkout is on `develop`, whose `server.json` still carries the previous version until main step 8 merges `main` back. After `git fetch origin main`, confirm `git diff origin/main HEAD` is empty and `server.json` shows the hotfix version, then run `mcp-publisher validate`/`publish` there. Remove the hotfix worktree and its branch after main step 8.
- **Main step 8's merge-back may conflict in `CHANGELOG.md`, and that's expected.** If the fix's own PR on `develop` added the entry as `## [X.Y.Z] — Unreleased` and step 3 dated it on the hotfix branch, resolve to the single dated entry. Any other conflict is the "stop and investigate" case in main step 8. (v0.9.5, 2026-10-24.)
