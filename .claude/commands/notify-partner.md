Wake this role's dev/QA partner directly, if they're already running as a live agent, instead of leaving the handoff to the user relaying it by hand. Invoked from `dev.md` and `qa.md` at each handoff point in their own flows (a PR going up, a fix being pushed, findings coming back) — not run standalone by a user, and never a blocking dependency: when no live partner session exists, this is a silent no-op and the existing fully-manual flow (the user invokes `/team-member <partner>` when ready, whose own reactive pickup logic — `qa.md`'s "find the partner Dev's open PR" / `dev.md`'s branch-state check — finds the same work regardless of how it got started) is completely unaffected.

**Partner pairing** (mirrors `team-member.md`'s own Partner column — Ash↔Sky, Jay↔Kit): resolve the caller's own name to its partner before anything else. There is no case where a role notifies anyone other than its fixed pairing partner from *this* file — QA never notifies Kai from here, and this mechanism doesn't extend to the non-lane-paired roles (Aziz/Amy/Joy/Bob), which have no partner to notify. (QA does wake Kai directly on a passing round, but via a separate, narrower mechanism — see `notify-kai.md`, wired into `qa.md` step 8 — not this one.)

1. `ListAgents`. Look for a row whose name matches the partner's name (`Sky`, `Kit`, `Ash`, or `Jay`) **case-insensitively** — a session can end up registered under whatever casing it was actually invoked with (e.g. `/team-member sky`), and `team-member.md`'s own argument matching is already case-insensitive on the way in, so requiring exact case here would silently treat a live partner as absent over nothing but a typing difference. Confirmed live 2026-08-20: a `ListAgents` call from a live Bob session showed peer rows named exactly `Sky` and `Jay` — sibling `/team-member` sessions on the same machine are visible this way even though this session never spawned them.
   - **No matching row:** nothing to do. Don't report this as a failure or ask the user to start one — the manual flow this mechanism sits on top of already handles it. Continue with whatever this role's own file says next.
   - **More than one row matches:** don't guess which is the real partner — ask the user rather than sending to either.
   - **Exactly one match:** proceed to step 2, addressing it by the row's own literal name as `ListAgents` returned it (not the canonical capitalized form above) — `SendMessage`'s own routing may itself be case-sensitive even though this step's detection isn't, so send to whatever string actually identified the live row.
2. `SendMessage({to: "<PartnerName>", message: "<content>"})`. Keep the content to the triggering fact only — a PR number and what just happened — not a restatement of the partner's own process: the receiving session re-derives its actual next steps from its own role file once it acts on the message, the same as if the user had just invoked `/team-member <partner>` at that exact moment. This is unlike `qa-kickoff.md`'s message block, which must be verbatim because a *human* types it into the CLI; this message is read by a peer *agent*, which parses natural language fine, so don't over-specify it into a rigid script.
   - **Dev → QA, first pass** (after opening a PR): e.g. `"PR #<n> is up for issue #<n>. Ready for your QA pass."`
   - **Dev → QA, re-verification** (after pushing a fix for a named finding): e.g. `"Pushed a fix for <finding, one clause> on PR #<n>. Ready for re-verification."`
   - **QA → Dev, findings** (after commenting a failed pass on the PR): e.g. `"QA found issues on PR #<n> — see the PR comment for what failed."`
   - There is no **QA → Dev, passed** case: a passing QA round hands off to Kai via the `qa-approved` label, not back to the Dev partner, who has nothing further to do once QA approves.
3. Fire-and-forget: don't wait for a reply and don't poll `ListAgents` to see whether the partner picked it up — `SendMessage` already documents that messages enqueue and drain at the receiver's own next turn, whether it's idle or mid-task right now.
