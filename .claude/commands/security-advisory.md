Run a vulnerability fix through a private GitHub security advisory, from the confirmed report to the published advisory. Kai owns the run and invokes this command; the other roles each have a section below. Every role that touches the fix reads this file, so whoever picks up the fork PR finds the rules here and doesn't need them passed along in a hand-off message.

Why this exists: the first advisory fix (2026-10) worked, but its rules lived only in Kai's messages. Each hand-off, and each `/clear`, meant the human had to paste them into the next session.

## Rules that hold for the whole run

1. **Nothing public until the advisory is published.** No public issue, PR, PR comment, commit to `develop`, roadmap entry, memory pointer in a public file, or label that describes the vulnerability. This includes indirect tells: a public ticket held because it overlaps the fix gets a neutral hold comment ("held, overlaps in-flight work, Kai will re-RFD"), never the reason. Discussion goes on the private fork's PR or in the advisory's own comments.
2. **The work lives on the advisory's private fork** (`<owner>/<repo>-ghsa-xxxx-xxxx-xxxx`, created from the advisory page with "Start a temporary private fork"). Each role worktree adds it as a remote named `ghsa` (`git remote add ghsa https://github.com/<owner>/<repo>-ghsa-…git`). The fix branch keeps the normal naming (`fix/<dev>/ghsa-<short-id>`).
3. **CI doesn't run on the fork.** Dev and QA each run `uv run python -m pytest` locally and record the pass/skip counts in the PR description or QA comment. That replaces the CI gate in `merge-pr.md`.
4. **QA routing is by explicit hand-off, not branch name.** `qa.md`'s partner-PR lookup runs `gh pr list` against the public repo, so it never finds a fork PR. Kai (or the Dev, via `/notify-partner`) names the fork PR and points at this file. The QA session still needs its usual go-ahead (`qa.md`).
5. **The verdict goes on the fork PR, as a review.** GitHub forbids plain comments on an advisory's temporary private fork: `gh pr comment` fails with "This action is forbidden on workspace repositories" (confirmed 2026-10-03). Use `gh pr review <n> --repo <fork> --comment --body-file <file>` for both send-backs and the approval; the approval review opens with "QA approved" and lists the cases run. `--approve` won't work either, because every team PR is authored by the same GitHub account. Never label or comment on a public PR. Then QA tells Kai directly (`/notify-kai`), or the Dev (`/notify-partner`) on a send-back.
6. **Only the human merges.** The fork PR is merged from the advisory page ("Merge pull request"), not with `gh pr merge` and not by Kai. GitHub merges it into the public default branch right away, *before* the advisory is published: from that moment the fix commit and its message are public. Keep the window between merge and publication as short as possible (steps 6–8 below in one sitting), and keep the commit message and test comments factual, describing the defect without a step-by-step exploit.

## Steps

1. **Kai — set up.** After the human confirms the report: create the private fork from the advisory page, set the advisory's affected range, and note the CWE. Pick the Dev and QA lane (the lane whose open work overlaps the fix least). Put any overlapping public tickets on a neutral hold (rule 1).
2. **Kai — hand off to Dev.** Send the Dev the fork URL, the advisory ID, and "follow `.claude/commands/security-advisory.md`". Nothing else needs restating.
3. **Dev — fix.** Normal `dev.md` flow with these changes: branch from the fork's default branch, push to `ghsa`, open the PR against the fork (`gh pr create --repo <fork>`), run the local suite (rule 3), and add a QA test case to `docs/qa/tests/` in the same PR, as usual. Then wake QA with the fork PR's URL.
4. **QA — verify.** Normal `qa.md` pass, with step 1 reading `git fetch ghsa <branch> && git reset --hard FETCH_HEAD` and step 4 including a live probe that reproduces the original report against the fixed code. Clean up every probe file in Drive and on disk afterwards. Findings go back to the Dev on the fork PR, same bar as any PR. On a pass: rule 5.
5. **Kai — pre-merge check.** Confirm the fork PR has QA's comment, the local suite counts, and no conflict with current `develop`. Tell the human it's ready to merge from the advisory page.
6. **Human — merge** from the advisory page.
7. **Kai — confirm and release.** Confirm the merge landed on `develop`, lift the holds from step 1, and start a patch release (`/release`, with Aziz's sign-off).
8. **Kai — publish.** After the release is on PyPI, set the advisory's patched version and ask the human to publish it (and request a CVE if wanted). Any QA-results PR or follow-up ticket that mentions the vulnerability can go public only after this.
9. **Follow-ups.** Codebase rules the fix implies (e.g. a new `CLAUDE.md` invariant) go through the normal flow after publication: a ticket, or Bob's gate for process files.
