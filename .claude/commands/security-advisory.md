Run a vulnerability fix through a private GitHub security advisory, from the confirmed report to the published advisory. Kai owns the run and invokes this command; the other roles each have a section below. Every role that touches the fix reads this file, so whoever picks up the fork PR finds the rules here and doesn't need them passed along in a hand-off message.

Why this exists: the first advisory fix (2026-10) worked, but its rules lived only in Kai's messages. Each hand-off, and each `/clear`, meant the human had to paste them into the next session.

## Rules that hold for the whole run

1. **Nothing public until the advisory is published.** No public issue, PR, PR comment, commit to `develop`, roadmap entry, memory pointer in a public file, or label that describes the vulnerability. This includes indirect tells: a public ticket held because it overlaps the fix gets a neutral hold comment ("held, overlaps in-flight work, Kai will re-RFD"), never the reason. Discussion goes on the private fork's PR or in the advisory's own comments.
2. **The work lives on the advisory's private fork** (`<owner>/<repo>-ghsa-xxxx-xxxx-xxxx`, created from the advisory page with "Start a temporary private fork"). Each role worktree adds it as a remote named `ghsa` (`git remote add ghsa https://github.com/<owner>/<repo>-ghsa-…git`). The fix branch keeps the normal naming (`fix/<dev>/ghsa-<short-id>`). **Every push in this run goes to `ghsa`, never `origin`, including QA's Result-entry pushes.** Wherever a role file says `origin` (e.g. `qa.md` steps 1, 6, 7, 8), read `ghsa`.
3. **CI doesn't run on the fork.** Dev and QA each run `uv lock --check`, `uv run ruff check .`, `uv run ruff format --check .`, and `uv run python -m pytest` locally, and record the results (pytest pass/skip counts included) in the PR description or QA review. That replaces the CI check, including `qa.md` step 8's CI wait.
4. **QA routing is by explicit hand-off, not branch name.** `qa.md`'s partner-PR lookup runs `gh pr list` against the public repo, so it never finds a fork PR. Kai (or the Dev) names the fork PR by its full URL, never a bare `#<n>` (fork PR numbers overlap the public repo's), and points at this file. The QA session still needs its usual go-ahead (`qa.md`).
5. **The verdict goes on the fork PR, as a review.** GitHub forbids plain comments on an advisory's temporary private fork: `gh pr comment` fails with "This action is forbidden on workspace repositories" (confirmed 2026-10-03). Use `gh pr review <n> --repo <fork> --comment --body-file <file>` for both send-backs and the approval, with `qa.md`'s first line (`## QA round <N> (<Name>) @ <short-sha>: sent back` or `: approved`) and, on an approval, the cases run. `--approve` won't work either, because every team PR is authored by the same GitHub account. The fork has no labels, so no `qa-approved` is applied, and never label or comment on a public PR. Then message Kai (on a pass) or the Dev (on a send-back) directly with `SendMessage`, giving the fork PR's full URL. Don't run `/notify-kai`: it's scoped to the `qa-approved` label, which this run never applies.
6. **Only the human merges.** The fork PR is merged from the advisory page ("Merge pull request"), not with `gh pr merge` and not by Kai. GitHub merges it into the public default branch right away, *before* the advisory is published: from that moment the fix commit and its message are public. Keep the window between merge and publication as short as possible (steps 6–8 below in one sitting), and keep the commit message and test comments factual, describing the defect without a step-by-step exploit.

## Steps

1. **Kai — set up.** After the human confirms the report: create the private fork from the advisory page, set the advisory's affected range, and note the CWE. Pick the Dev and QA lane (the lane whose open work overlaps the fix least). Put any overlapping public tickets on a neutral hold (rule 1).
2. **Kai — hand off to Dev.** Send the Dev the fork URL, the advisory ID, and "follow `.claude/commands/security-advisory.md`". Nothing else needs restating.
3. **Dev — fix.** Normal `dev.md` flow with these changes: branch from the fork's default branch, push to `ghsa` (rule 2), open the PR against the fork (`gh pr create --repo <fork>`), run the local checks (rule 3), and add a QA test case to `docs/qa/tests/` in the same PR, as usual. Then wake QA with the fork PR's full URL (rule 4).
4. **QA — verify.** Normal `qa.md` pass, with these changes. `qa.md`'s step 1 reset is two commands: `git fetch ghsa <branch>`, then `git reset --hard FETCH_HEAD`. `qa.md`'s step 4 includes a live probe that reproduces the original report against the fixed code. Every push goes to `ghsa` (rule 2), and rule 3's local checks replace the CI wait. Clean up every probe file in Drive and on disk afterwards. Findings go back to the Dev on the fork PR, same bar as any PR. Verdict and hand-off: rule 5.
5. **Kai — pre-merge check.** Confirm the fork PR has QA's approval review, the local check results, and no conflict with current `develop`. Tell the human it's ready to merge from the advisory page.
6. **Human — merge** from the advisory page.
7. **Kai — confirm and release.** Confirm the merge landed on `develop`, lift the holds from step 1, and start a patch release (`/release`, with Aziz's sign-off). If `develop` holds unreleased work that shouldn't ship in a security patch, the patch is a **hotfix backport** instead:
   - The Dev ports the fix by hand onto the last release tag, as branch `release/<x.y.z>-hotfix` on the fork, with base branch `release/<x.y.z>` pointing at the tag. The fork rejects a PR whose base isn't `develop`, and its compare API returns 404 (both confirmed 2026-10-03, during the GHSA-hx2f backport), so the backport is reviewed as a **branch, not a PR**: `git diff v<last>...FETCH_HEAD`. The Dev's wake to QA carries the branch, the base, and the differences from the `develop` version. The human pastes that message into the QA session in full, since a new session can't see it.
   - QA reviews it in a **fresh session** (one review per session). Read `qa.md` and this file *before* resetting the worktree: the reset swaps every process file for the old tag's version. Live QA needs the server to run the branch's code, so reconnect after the reset, as usual. The test case's `**Result**` entries from `develop` don't carry over; record new ones on the branch. QA's verdict can't go on a PR, so it goes to Kai and the Dev by message, plus a `**Result**` commit pushed to the branch on `ghsa`.
   - Aziz signs off the release, and Kai tags `v<x.y.z>` from the hotfix branch.
8. **Kai — publish.** After the release is on PyPI, set the advisory's patched version and ask the human to publish it (and request a CVE if wanted). Any QA-results PR or follow-up ticket that mentions the vulnerability can go public only after this.
9. **Follow-ups.** Codebase rules the fix implies (e.g. a new `CLAUDE.md` invariant) go through the normal flow after publication: a ticket, or Bob's gate for process files.
