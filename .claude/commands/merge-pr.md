Merge the current branch's PR and clean up its worktree. Uses `--admin` only to bypass the required-review gate (this is a solo-maintainer repo, so a second approver is never coming) — it must never be used to bypass a failing or pending status check.

1. Get the PR: if given a PR number (e.g. following on from `/verify-pr <number>`), use `gh pr view <number> --json ...` explicitly rather than relying on current-branch detection — `/verify-pr` may have checked out a locally-named `review/<headRefName>` branch (see its step 3) instead of the PR's real branch name, which current-branch auto-detection can't always resolve. Otherwise, get the PR for the current branch: `gh pr view --json number,title,url,state,mergeable,statusCheckRollup,reviewDecision,isDraft`. If there's no open PR for this branch/number, stop and tell the user.
   - **Kai-specific case:** Kai runs this from the main checkout, which lives on `develop`, never on a ticket branch — so "current branch" detection can never resolve a PR for Kai's own invocations. If the user says something like "the PR is ready" or "merge it" with no PR number and no ticket branch checked out, don't guess which PR they mean from conversational context (e.g. defaulting to whichever PR was most recently discussed) — resolve it from actual state instead: `gh pr list --state open --label qa-approved`. Exactly one result is the PR. Zero or more than one: stop and ask, listing the candidates by number and title. (Confirmed live 2026-07-25: an ambiguous "pr is ready for merge" got matched to the wrong PR — a dependabot bump that had just been discussed — instead of the one actually carrying `qa-approved`.)
2. Verify it's actually safe to merge:
   - `state` must be `OPEN`.
   - Every check in `statusCheckRollup` must show success. If anything is failing or still pending, stop and report which — do not merge, and do not wait/poll.
   - Specifically confirm a `"name": "Lint and test"` entry is *present* in `statusCheckRollup` with `"conclusion": "SUCCESS"` — don't just scan for failures. This check has been observed missing entirely from the rollup (not failing, not pending — absent) on a PR's first push, while CodeQL's checks still populated normally; a rollup with zero failing entries can still mean the actual test suite never ran. If it's absent, don't treat that as a pass — push a trivial commit (or `gh workflow run ci.yml --ref <branch>` if available) to retrigger it and wait for a real result before merging.
   - `mergeable` must not be `CONFLICTING`. `UNKNOWN` is not a block — GitHub computes this asynchronously and it can lag briefly right after a label change or a fresh push (confirmed on PR #324); re-run `gh pr view <number> --json mergeable` once after a few seconds and it should resolve to `MERGEABLE` or `CONFLICTING`.
   - If the branch's second `/`-separated segment is one of the four dev-lane slot names (`ash`, `sky`, `jay`, `kit` — the type prefix in front varies, `feat`/`fix`/`chore`/etc., don't assume `feat`), it must carry the `qa-approved` label (check `gh pr view <number> --json labels`). If it doesn't, stop — that means the paired QA agent (`/team-member`) hasn't signed off yet; don't merge and don't review it yourself here. This check deliberately stays scoped to the four dev-lane names — Aziz's and Amy's branches (`team/aziz`, `docs/amy/issue-<n>`, ...) aren't part of the Dev/QA pairing and go through normal review instead.
     - **Exception:** a QA-named slot (`sky`/`kit`) authoring its own process/meta PR (e.g. `chore/sky/...`) has no natural QA partner to self-approve — the Dev/QA pairing only exists for the *other* lane's ticket work. There's no label path for this case; stop and ask the user directly whether it's safe to merge without one, same as any missing-label PR. If they confirm (e.g. because it's a prompting/process change with no application-code risk), proceed — that confirmation stands in for the label for this PR only, it doesn't waive the check generally.
3. If the PR is authored by `app/dependabot` (branch prefixed `dependabot/`): give it a quick security peek before summarizing. This is specifically to compensate for a gap in Dependabot's own pipeline — its `cooldown` setting (`.github/dependabot.yml`) only throttles scheduled *version* updates; security updates (this repo has `dependabot_security_updates` enabled) bypass cooldown entirely by design, so a same-day "fix" release can reach a PR here with zero time for the community to have caught a compromised release. Dependabot's own vetting stops at "does this version satisfy the advisory's patched range" — nothing upstream checks the release itself.
   - Read the PR body: it names the advisory (GHSA/CVE) and links the release notes/changelog — confirm the bump target is actually the version the advisory identifies as patched, not something Dependabot rounded up to.
   - Check who published the target release and when (`gh api repos/<owner>/<repo>/releases` for GitHub-hosted packages, or the registry's own upload metadata for others, e.g. PyPI's `https://pypi.org/pypi/<pkg>/<version>/json` → `urls[].upload_time_iso_8601`) — the goal is the same protection cooldown gives version-update PRs automatically (time for the community to flag a bad release), just done by hand here since security updates bypass cooldown entirely.
   - Skim the actual diff between the vulnerable and patched version (the linked changelog/release notes usually suffice; for anything that looks unusual, diff the two source tags directly) rather than trusting the version bump alone.
   - This is a quick sanity check, not a full audit — flag anything that looks off to the user rather than silently blocking, and don't hold up an otherwise-clean bump over it.
4. Show the user a summary: PR number, title, URL, check status, and review status (expected to be blocked only on the missing-approval requirement). State plainly that merging will use `--admin` to bypass that review gate. Ask for explicit confirmation before proceeding. Confirmation must be an unambiguous yes — a frustrated, sarcastic, or otherwise non-answering reply to this prompt is not consent; ask again plainly rather than treating it as a green light. (Confirmed live 2026-07-25: an angry non-answer got read as "just do it" and produced an `--admin` merge without real approval.)
5. On confirmation: if `isDraft` was `true`, mark it ready first — `gh pr ready <number>` — `gh pr merge --admin` refuses a PR still marked draft, it doesn't auto-ready it. Then squash-merge (matching this repo's existing history — commits land on `develop` as a single `title (#number)` commit): `gh pr merge <number> --admin --squash`. The remote branch is auto-deleted on merge (repo setting), so don't pass `--delete-branch`.
6. Clean up:
   - If the merged branch's second segment matches any of the persistent dev-team slot names — the full `WORKTREE_ROLES` list in `scripts/setup_team.sh` (`ash`, `sky`, `jay`, `kit`, `aziz`, `amy`, `joy`, `bob`), not a hand-copied subset of it — again, regardless of its type prefix — **do not remove the worktree**: it's a persistent slot, not a one-off. (This list previously hardcoded only six names and silently excluded `joy` and `bob`; a merged `doc/joy/...`/`docs/bob/...`-style PR would have fallen through to the manual-cleanup branch below and had its persistent worktree removed. Check `scripts/setup_team.sh` directly if this list and that array ever disagree again.) Before switching away, check the just-merged branch itself for commits the squash-merge didn't capture: `git fetch origin develop` then, still on the ticket branch, `git log --oneline origin/develop..HEAD`. A squash-merge lands as one commit on `develop`, so anything pushed to the PR branch in the window between CI going green and the merge landing — a worker or QA session racing the merge — won't be in it even though it's on the branch you're about to delete (confirmed: PR #353 had a CLAUDE.md commit pushed 12s *after* the merge; `git branch -d` would have silently discarded it). For each such commit, cherry-pick it onto current `origin/develop` from the main checkout (empty cherry-pick = already landed some other way, nothing to do) before proceeding. Note that `git log --oneline origin/develop..HEAD` lists the ticket branch's *entire* commit history after any squash merge — that's expected and not itself a signal, so don't iterate cherry-picks over every commit listed there, especially on a branch with several commits. A faster, equally safe check: scope a diff to just the PR's own files (`gh pr view <number> --json files`) between the squash-merge commit and the branch tip (`git diff <merge-commit> <branch-tip> -- <files...>`). An empty diff, or one that only shows removals (content present in the merge commit but not the branch tip), means the branch tip is simply stale relative to what got merged — normal when QA pushed Result-entry or fix commits straight to the remote PR branch after this worktree's last local sync (confirmed 2026-07-21, PRs #380/#385/#386: every case was this stale-local pattern, nothing was actually lost) — and nothing needs rescuing. Only if the scoped diff shows *additions* — content on the branch tip absent from the merge commit — does that identify real at-risk work; find which specific commit introduced it and cherry-pick only that one, rather than blindly cherry-picking the full list. Only once that's clear: `git checkout team/<name>`, `git reset --hard origin/develop`, then delete the just-merged branch by its actual name (`git branch --show-current` before switching, or read it off the PR's `headRefName` — don't assume it starts with `feat/`). Report that the slot is back to idle, ready for its next ticket.
   - If the current branch is a `review/<headRefName>` branch created by `/verify-pr` (not a `.claude/worktrees/*` worktree — just a local branch in the main checkout), there's no worktree to remove: switch to `develop` and `git branch -D review/<headRefName>`.
   - If this session created the current worktree (i.e. it got here via `/start-worktree` or `/next-issue` earlier in this same session), use `ExitWorktree` with `action: "remove"`.
   - Otherwise (worktree predates this session), fall back to manual cleanup from the main checkout: `git worktree remove <path>`, then `git branch -d <branch>`, then `git worktree prune`.

   This step only ever touches the lane whose PR was just merged — Kai completing its own action, not reaching into another lane's independent state. Detecting a sibling lane that raced the same ticket without ever opening a PR is that lane's own job: `dev.md`'s self-heal checks whether the issue behind its current branch is already closed by someone else's merge, not something Kai sweeps for post-merge (see [[feedback_worktree_self_heal]] for why an external, commit-message-matching sweep was removed — it produced a false positive on every routine QA branch copy).
7. From the main checkout on `develop`, `git pull` — unconditionally, even if step 8 turns out to be a no-op. `gh pr merge` merges via the API; it never touches the main checkout's local branch, so skipping this leaves Kai's live-testing home base stale until the next unrelated pull happens to catch it up.
8. Update the roadmap: check `docs/roadmap.md` for a checkbox line referencing the issue(s) this PR closes (search by issue number). If found, check it off (`- [ ]` → `- [x]`) and append `(PR <number>)` in the existing style (e.g. `(PR #280)`) — see recent `- [x]` entries for the exact convention. If the roadmap has no line item for this issue (not every ticket is roadmap-tracked — chores, follow-up defects, etc.), skip this step silently. Commit directly to `develop` (`docs(roadmap): check off #<issue> (PR <number>)`) and push — `develop`'s branch protection has `enforce_admins: false`, so a direct push by the repo owner is allowed for this kind of small, reversible, docs-only change; don't open a separate PR for it.
9. If step 6 reported a dev-lane slot (`ash`/`sky`/`jay`/`kit`) back to idle, check whether that lane already has its next ticket queued: `gh issue list --state open --label ready-for-development --label lane-a` (or `lane-b` for `jay`/`kit`). If one is already labeled, nothing to do. Otherwise, figure out its next ticket:
   - Check the active roadmap-planning memory (memory index, not a hardcoded filename) for phase order, then cross-reference `docs/roadmap.md`'s current `- [ ]`/`- [x]` state for that lane's queue — the memory can be stale (bugs ship out of the order it recorded, tickets get re-triaged), so the roadmap doc's live checkbox state is the tiebreaker, not the memory.
   - First, check `gh issue list --state open --label solo-only --label ready-for-development`. If that returns anything, stop here — per `kai.md`'s ticket-triage section, no other ticket gets `ready-for-development` while a `solo-only` ticket holds it, regardless of how many lanes are idle. This is not a judgment call to weigh against file overlap; treat any hit as an unconditional hold, and don't attempt the rest of this step until it ships.
   - Only once that's clear, confirm the candidate is otherwise unblocked: no unresolved dependency noted against it, and no real file/surface conflict with whatever the other lane currently has in flight.
   - If exactly one ticket is the unambiguous front of that lane's queue, label it `ready-for-development` plus the matching lane label — no separate confirmation needed, same reasoning as step 8's unprompted roadmap commit: a label is small and reversible.
   - If there's a real judgment call instead — more than one plausible candidate, a defect-vs-enhancement ordering question, a cross-cutting conflict, or the memory and the roadmap disagree about what's next — stop and ask the user rather than guessing; report the candidates and the reason it's not a clean call.
10. Report a summary: the merge commit, the now-merged PR URL, confirmation the worktree was removed, whether the roadmap was updated, and whether a next ticket was queued for the now-idle lane (or why not).
