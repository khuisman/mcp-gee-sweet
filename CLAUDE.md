# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Run locally from the cloned repo:
```bash
uv run mcp-gee-sweet
uv run mcp-gee-sweet --transport sse   # SSE instead of stdio
```

Build and publish:
```bash
uv build       # produces dist/*.whl
uv sync        # install deps from uv.lock
```

Docker:
```bash
docker build -t mcp-gee-sweet .
docker run --rm -p 8000:8000 \
  -e CREDENTIALS_CONFIG=<base64> \
  -e DRIVE_FOLDER_ID=<id> \
  mcp-gee-sweet
```

Tests live in `tests/` and can be run with `uv run pytest`.

## Architecture

Logic is split across `src/mcp_gee_sweet/`: `server.py` (MCP setup, tool decorator, resources), `auth.py` (lifespan, `SpreadsheetContext`), and `tools/` (domain-based layout):

- `tools/sheets/data.py` — read/write cell data (`get_sheet_data`, `get_sheet_formulas`, `get_multiple_*`, `find_in_spreadsheet`, `clear_values`, `update_cells`, `batch_update_cells`, `batch_update`)
- `tools/sheets/structure.py` — sheet structure (`list_sheets`, `copy_sheet`, `duplicate_sheet`, `rename_sheet`, `create_sheet`, `delete_sheet`, `add_rows`, `add_columns`, `delete_rows`, `delete_columns`, `hide_rows`, `unhide_rows`, `hide_columns`, `unhide_columns`, `resize_rows`, `resize_columns`, `format_cells`, `update_borders`, `add_data_validation`, `get_data_validation`, `merge_cells`, `unmerge_cells`, `freeze`, `update_sheet_properties`, `sort_range`, `add_chart`)
- `tools/sheets/helpers.py` — A1 notation helpers (`_parse_a1_notation`, `_column_index_to_letter`, etc.)
- `tools/drive/files.py` — file/folder operations (`create_spreadsheet`, `import_csv_to_sheet`, `list_spreadsheets`, `list_files`, `search_files`, `create_folder`, `create_shortcut`, `copy_file`, `move_file`, `rename_file`, `star_file`, `unstar_file`, `delete_file`, `restore_file`, `empty_trash`, `list_shared_with_me`, `list_recent_files`, `get_storage_quota`, etc.). `star_file`/`unstar_file` (#139) set `starred` via `files().update` — neither `get_file_metadata` nor `list_files` currently exposes the `starred` field back, so live QA verification is round-trip only (see TC-D202/203 in `docs/qa/tests/drive.md`). Both `list_files` and `get_file_metadata` now surface Drive's `md5Checksum` field as `md5_checksum` (#274) — `None` for Google Workspace files (Docs/Sheets/Slides have no fixed byte content, so the Drive API omits the field for them), a real hash for binary files. Exists so callers can detect real content drift instead of inferring it from `modifiedTime`, which sync/upload paths don't always keep faithful to actual content (see `transfer.py`'s `sync_folder` `use_checksum` param below, the primary consumer of this).
- `tools/drive/sharing.py` — permissions (`share_spreadsheet`, `share_file`, `list_permissions`, `update_permission`, `remove_permission`, `transfer_ownership`). `transfer_ownership` requires OAuth — service accounts have no personal Drive identity to transfer ownership to/from, so Drive's API rejects the transfer.
- `tools/drive/transfer.py` — upload/download/sync/export/revisions; `_upload_local_file` (the core behind the `upload_local_file` tool) is a module-level helper so `docs/images.py`'s `insert_local_images` can call it directly, imported cross-package the same way `docs/content.py` imports `_SA_QUOTA_ERROR` from `tools/drive/__init__.py`. `upload_local_file`'s `convert` param (#188) requests Drive's *native* import conversion — CSV/XLSX→Sheets, DOCX/MD/HTML→Docs, PPTX→Slides — by uploading with the source format's mimeType while setting the destination's `mimeType` metadata to the target Google Workspace type (`_CONVERT_MIME` maps extension → (source mime, target mime)). This is a different mechanism from `docs/content.py`'s `create_doc_from_file`, which parses the file locally and rebuilds it via Docs API requests instead of Drive's importer — don't conflate the two when adding new conversion paths. `sync_folder`'s `convert_markdown` param (#211) applies the same native-conversion mechanism to local `.md` files during sync uploads. Because the converted Doc keeps its `.md` name in Drive, `_sync_level`'s drive_map-building loop matches it back to the local `.md` file directly (bypassing the export_format-suffix scheme normal Workspace files need) so resyncs settle into "in sync" instead of re-uploading a duplicate every run — this also reopens matching for a drive-only converted Doc with no local counterpart and no `export_format` (previously unreachable, since such files were always excluded from `drive_map`) — the plan-building loop classifies that case as a `conflict` (a convert_markdown Doc has no reverse conversion) before it ever reaches the download branch, so the download branch's own `_EXPORT_MIME[None]` guard is defensive-only dead code in the current implementation, not a reachable path (confirmed live: TC-D221). There is no reverse conversion (Doc → markdown). A converted Doc is recognized on every later sync via a Drive `properties` marker (`_CONVERT_MARKDOWN_SOURCE_PROP`) stamped at creation time by both `_sync_level`'s own upload path and `_upload_local_file`'s `convert=True` path (#414 rounds 2-3) — recognition is deliberately independent of whether the *current* call passes `convert_markdown`/`convert`, since the Doc's own persisted property is what matters, not this call's flag. Three further edge cases from that round-3 review shipped as issue #422: the `drive_map`-building loop now detects (rather than silently resolving) a name collision between a plain file and a converted Doc, reporting it under `failed` instead of letting whichever is listed last win the slot and make the other invisible to the sync; `_upload_local_file` now stamps `modifiedTime` from the local file's mtime on a converted Doc (via `create()` then a metadata-only `update()`, mirroring `_sync_level`'s own create() branch, since Drive's native import-conversion overwrites the create()-time value once conversion finishes) so a subsequent `sync_folder` lands in `skipped` rather than `conflicts`; and the drive-only branch now checks `direction` before `_is_converted_md`, so `direction='upload'` reports a plain `skip` like any other drive-only file instead of always reporting `conflict`. PR #433's own review round found the collision guard needed to go further: it originally only fired when the two colliding entries' `_is_converted_md` differed (a plain file vs. a converted Doc, #422's own reported shape), silently overwriting a same-type collision (two plain files, or two converted Docs, sharing a name) the exact same way; it now fires on any duplicate name regardless of type. The collision case is also now routed through the normal `plan`/`action` machinery (a new `"collision"` action, mapped to `conflict` during `dry_run` and to a real `failed` entry — `kind: "collision_fail"` — once execution is actually attempted) rather than writing to `failed` directly from the `drive_map`-building loop: that direct write both leaked into `failed` during `dry_run` (breaking the "dry_run never reports failures, only previews" invariant the pre-existing folder-collision failure path already upholds) and silently dropped a *local* file sharing the colliding name from every result list, since the plan loop's bare `continue` skipped it with zero acknowledgment. Separately, `_upload_local_file`'s `create()`+`update()` pair now shares one broad `except Exception` returning `{"error": ...}` (matching `_sync_level._run_one`'s own create+update pattern) instead of only catching quota `HttpError`s and letting everything else — including a failure in the new metadata-only restamp `update()`, after `create()` already succeeded — propagate uncaught to `upload_local_file`, which has no try/except of its own. `sync_folder`'s `use_checksum` param (#274) adds a content check ahead of `_sync_level`'s mtime comparison for names present on both sides: when the local file's md5 (`_local_md5`, streamed in 1 MiB chunks) matches Drive's own `md5Checksum` (now fetched by `_list_drive_children`), the pair is treated as in sync regardless of `modifiedTime` drift — this is what actually fixes `upload_local_file` not stamping `modifiedTime` (unlike `_sync_level`'s own upload path) causing a spurious re-download of identical content on the next sync, not just a same-mtime coincidence. Only applies where Drive returns a real `md5Checksum` — Workspace files and `convert_markdown` Docs have none and always fall back to mtime-only comparison, flag or no flag. A checksum *mismatch* doesn't force any decision by itself; it just falls through to the same mtime-based upload/download/conflict logic used when `use_checksum=False`, since content differing doesn't by itself say which side is newer. PR #472's own review round found four issues in this first version: the checksum comparison ran unconditionally, before the (cheap) mtime diff, including for pairs already within `_SYNC_MTIME_TOLERANCE` and even during `dry_run=True` — fixed by moving the mtime diff first and gating the hash read on `use_checksum and not dry_run and abs(diff) > _SYNC_MTIME_TOLERANCE`, so an already-in-sync pair or a dry_run preview never pays for a read it can't change the outcome of; `_local_md5` had no try/except unlike every other per-item operation in this module, so a file that became unreadable (deleted, permission-denied) between the directory scan and the hash read raised uncaught out of the whole `sync_folder` call instead of degrading to one `failed` entry — fixed via a new `"checksum_read_fail"` plan action mirroring the existing `"collision"` pattern; and `_upload_local_file`'s plain (non-`convert`) branch was identified as the actual root cause worth fixing directly — it never stamped `modifiedTime` the way the `convert_mime` branch three lines above already did (and `#422` already established for that branch), so a file uploaded through it always read as "Drive newer" on the very next `sync_folder` regardless of content — now stamped unconditionally in the `create()` body for every upload (no follow-up `update()` needed for the plain case, since Drive only overwrites `modifiedTime` when import-conversion is involved). `use_checksum` remains valuable beyond that root-cause fix for causes of drift the mtime stamp doesn't cover (e.g. a local overwrite that happens to preserve mtime). One review finding was accepted as a known tradeoff rather than fixed: a checksum mismatch that resolves to `'upload'` reads the local file twice (once to hash, once via `MediaFileUpload` for the actual transfer) — avoiding it would mean buffering the whole file in memory to share across both reads, a worse tradeoff for large files than one extra (likely page-cache-warm) disk read. `upload_local_folder` (#411) used to have its own independent inline upload loop with no `convert` param, unreachable from `_upload_local_file`'s conversion mechanism — bulk-importing a folder of CSV/DOCX/PPTX into native Workspace formats required falling back to per-file `upload_local_file` calls. Fixed by routing each candidate through `_upload_local_file` itself, gaining the same `convert` param and its semantics (an unsupported extension lands in `failed` rather than uploading as-is, matching `upload_local_file`'s own error-not-silent-fallback behavior). The existing bulk `skip_if_exists` pre-check (one `list()` call for the whole folder, not one per file — TC-D100) is preserved rather than replaced by `_upload_local_file`'s own per-call check: the folder loop now fetches each existing file's `mimeType` alongside its name in that same single call, decides skip-worthiness itself (name-only match when `convert=False`; name *and* target-mimeType match when `convert=True`, mirroring `_upload_local_file`'s own convert-aware duplicate check), and then calls `_upload_local_file` with `skip_if_exists=False` for whatever survives — so existence is never checked twice. `sync_folder(dry_run=True)`'s response used to duplicate every `skip`/`conflict` name into both a flat list (`skipped`/`conflicts`) and a full `{name, action, reason}` entry in `actions`, deterministically tripping the response-size cap on a moderately-sized, mostly-in-sync folder even though `actions` alone (name + action-type + reason for every item, including upload/download entries the flat lists never populated during `dry_run` in the first place) was already a complete, non-redundant picture (issue #512). Fixed by leaving `uploaded`/`downloaded`/`skipped`/`conflicts`/`failed` empty during `dry_run` rather than trimming or toggling `actions` itself. Separately, `sync_folder` previously had no response-size-cap bypass at all (`local_path_available=False`) unlike every other capped tool except `export_file`/`list_file_activity` (both deliberately, per the decision doc below) — its own `local_path` param already means the sync destination, so it can't double as a dump target the way `get_sheet_data`'s `local_path` does. Fixed by adding a separate `result_local_path` param following the same unconditional-if-passed `write_capped_result_to_disk` pattern as every other capped tool with a bypass; `enforce_response_size_cap` gained a `local_path_param` override so its error message names the right parameter instead of hardcoding `local_path`. PR #518's own QA review round live-caught a gap in that first version: `result_local_path` had no guard against pointing at or inside `local_path` — since `local_path` is scanned as sync input on every call (unlike every other capped tool's local_path/result_local_path, which are pure output destinations), a manifest written there showed up as a new local-only file on the very next sync and would have been uploaded to Drive on a real run. Fixed by rejecting the call up front (`ValueError`, before any Drive API call) when `Path(result_local_path).resolve()` equals or is a descendant of the resolved `local_path`. `upload_file`'s `convert_to_doc` param implements the identical native-import-conversion trick as `_upload_local_file`'s `convert`/`_CONVERT_MIME` above, independently — raw text/markdown/html content instead of a local file, always targeting a Doc since there's no file extension to dispatch Sheets/Slides on — with no cross-reference between the two (issue #412). Fixed by sharing `_GOOGLE_DOC_MIME` as the single source of truth for the target mimeType literal both mechanisms write, plus explicit docstring cross-references at both call sites; the two code paths themselves stayed separate rather than being merged, since their actual upload semantics (raw content vs. local file, single target vs. extension-dispatched) differ enough that unifying them would cost more complexity than it'd save.

- `tools/docs/` — Google Docs package; `__init__.py` is a thin dispatcher that delegates to four submodules:
  - `docs/content.py` — helpers (`_md_to_html`, `_to_doc_requests`, `_html_to_doc_requests`) and tools (`create_doc`, `get_doc_content`, `write_doc_content`, `create_doc_from_file`, `update_doc_from_file`, `get_doc_structure`, `find_in_doc`). `insert_doc_text`/`delete_doc_range`/`insert_page_break`/`insert_softbreak_paragraph` moved to `docs/editing.py`, and `insert_inline_image`/`insert_local_images` moved into `docs/images.py` (#372, following #371's extraction of `named_ranges.py`) — `_collect_doc_paragraphs` moved alongside them into `docs/indices.py`, next to its own sibling low-level helper `utf16_len`, and the dead `_html_to_text` helper (no callers anywhere in the codebase, confirmed via a repo-wide grep before deleting it) was dropped rather than moved. `update_doc_from_file` (#341) combines `create_doc_from_file`'s server-side file reading (extension inference to markdown/html, or an explicit `content_format` override) with `write_doc_content`'s in-place clear+replace — the clear-then-insert mechanism (including the same-batch `insertText` style-inheritance quirk described below) was extracted out of `write_doc_content` into a shared `_replace_doc_content` helper so both tools have exactly one implementation of it, the same way `_apply_doc_content` is already shared by directly with `style_doc_range` — `_collect_doc_paragraphs` is a generator (so a caller can stop early once `max_results` is hit) that walks the Docs API body, trusting each `ParagraphElement`'s own `startIndex` when present and otherwise carrying the running offset forward rather than dropping that element, since the API doesn't always populate it (seen on a document's first element). `get_doc_structure` now also surfaces each paragraph's `headingId` (`paragraphStyle.headingId`) — confirmed live present on the default single-tab `documents.get()` response for both `TITLE`/`SUBTITLE` and `HEADING_1`..`6` paragraphs, no `includeTabsContent` needed. `create_doc`/`create_doc_from_file`/`write_doc_content` now run an automatic second pass (`_resolve_heading_anchors`, gated by the cheap `_has_pending_anchor_links` check so content with no `#`-links skips the extra API round trip entirely) after any conversion that left a GitHub/GitLab-style `#slug` heading-anchor link behind (issue #409): it resolves the anchor against the doc's own real headings via `anchors.resolve_heading_anchor` and rewrites it to a working `.../edit?tab=t.0#heading=<headingId>` jump link (an ordinary URL is sufficient — no `Link.headingId` API field needed, confirmed live), or strips the link (keeping the text plain) when no heading matches with reasonable confidence — a link silently pointing at the wrong section is worse than a plain, unlinked mention. This was a deliberate product decision to resolve anchors automatically rather than only exposing `headingId` and leaving matching to the calling agent — see `docs/design/heading-anchor-resolution.md` for the full rationale. PR #453's own QA round (`/code-review high` + live testing against a fixture with no table and no anchor on the doc's first element) caught two correctness bugs the first version's hand-rolled body walk had: it only inspected top-level `paragraph` elements (a heading or anchor link living inside a table cell was invisible to both `_has_pending_anchor_links` and `_resolve_heading_anchors`), and it required a run's own `pe.get("startIndex")`/`endIndex` to both be non-`None` (silently dropping an anchor that is, or is part of, the document's first body element — the Docs API omits `startIndex` there, the same quirk `_collect_doc_paragraphs` already handles). Fixed by `_walk_headings_and_anchor_runs`, a dedicated recursive walker mirroring `_collect_doc_paragraphs`'s own two correctness properties (table-cell recursion; carrying the running offset forward via character-by-character advance rather than trusting a run's own possibly-inconsistent `endIndex`) rather than reusing `_collect_doc_paragraphs` itself, since that generator's yielded shape (text + char-indices only) doesn't carry per-run link URLs or heading-paragraph style info and is used elsewhere (`find_in_doc`) in a way not worth risking a signature change for. `_has_pending_anchor_links` gained a second parameter (`tables: list[Table]`, walked via `_table_has_pending_anchor_link`, recursing into nested tables) since `fill_tables()` builds and executes table-cell requests separately from `content_requests`, invisible to the original single-argument guard. `create_doc`/`create_doc_from_file`/`write_doc_content` now support inline images in markdown (`![alt](src)`) and HTML (`<img>`) conversion (issue #333) via a shared `_apply_doc_content` helper: `src` may be a local filesystem path (uploaded to Drive), a `drive:<file_id>` reference to an already-uploaded file, or a public `http(s)://` URL (used directly) — resolved by `_resolve_image_source`, sharing local-path/`drive:` sources `anyone:reader` the same way `insert_local_images` already does, then (per explicit product decision, and now also `insert_local_images`'s own default — a behavior change from its original #332 shipped version) revoking that temporary share once the image is embedded, unless `revoke_sharing=False`. The Docs API rejects an entire `batchUpdate` atomically if any one `insertInlineImage` request in it can't be fetched (confirmed live via TC-DOC102's own deliberately-unreachable-URL case) — `_apply_doc_content` retries with the failing request stripped (its index is parsed directly out of Google's own error message) rather than losing every other request in the same call; see `docs/design/image-conversion.md` for the full design, including why `Image` is a zero-width AST node (not a marker) and the deliberate table-cell-image gap.
  - `docs/editing.py` — tools (`insert_doc_text`, `delete_doc_range`, `insert_page_break`, `insert_softbreak_paragraph`), extracted out of `content.py` (#372) as `content.py`'s text-range editing primitives, distinct from that file's remaining whole-document create/read/write concern. `insert_softbreak_paragraph` joins multiple lines with a literal `"\v"` (vertical tab) character in a single `insertText` call — confirmed live that the Docs API stores this as one paragraph element rather than splitting it, matching the Docs UI's own Shift+Enter soft-break convention — and sets `namedStyleType` explicitly over the inserted span rather than leaving it to whatever the insertion point would otherwise inherit.
  - `docs/images.py` — tools (`insert_inline_image`, `insert_local_images`) plus inline-image size validation/downscaling/error-clarification shared by every `insertInlineImage` call site (issue #400). The two tools moved here from `content.py` (#372) rather than into a differently-named module — issue #372 predates #400's creation of this file, and by the time it was picked up, `images.py` already existed here for the size-validation helpers, so merging avoided colliding with a newly-invented module name (an earlier version of this rationale claimed the two tools were already this module's "primary callers"; that doesn't hold up — `content.py`'s own `_resolve_image_source`, which stays there, depends on the exact same six helpers just as heavily). `insert_local_images` uploads local image files and swaps each into the doc at a plain-text marker in one call; confirmed live that `insertInlineImage` with a `drive_file_id` fails with "There was a problem retrieving the image" unless the file is first shared `anyone`/`reader` — the Docs backend fetches the image as an anonymous HTTP request, so being accessible to the authenticated user alone is not enough (this also applies to `insert_inline_image`'s own `drive_file_id` path). Google Docs rejects any inline image over ~25 megapixels or ~50MB with a bare `HttpError 400 "...The provided image is too large."` naming neither the actual limit nor the image's own size (confirmed against Google's documented ceiling: <https://developers.google.com/workspace/docs/api/how-tos/images>, 25 megapixels / 50MB / PNG-JPEG-GIF only). `check_dimensions`/`check_image_bytes` pre-validate and return a clear `{"error": ...}` naming the limit and the image's actual size before any upload/share/embed call happens; `downscale_image_bytes` (Pillow — see `docs/decisions/decision-pillow-image-dependency.md` for why it was added as a dependency) resizes in place, preserving format, and declines (`None`) rather than corrupting an animated GIF (`Image.resize` only touches the current frame). `check_image_bytes` originally only enforced the megapixel limit, not the byte-size one the module's own docstring already cited — a low-compressibility image (e.g. noise data) could be well under 25 megapixels but still over 50MB, passing pre-validation silently and only failing at the real `batchUpdate` call (issue #562, confirmed live via a real ~75MB-but-24-megapixel PNG). Fixed by adding `check_file_size`/`too_large_bytes_message` (the byte-size counterpart to `check_dimensions`/`too_large_message`) into `check_image_bytes`, and extending `downscale_image_bytes` with a bounded iterative shrink loop for the case where the megapixel-based scale factor alone is a no-op (the image is already within that limit) but the encoded result is still over the byte limit — unlike pixel count, encoded byte size isn't predictable from a single scale factor since it depends on compression, not just dimensions. The two Drive-metadata-only size checks (`insert_inline_image`'s `drive_file_id` path here, `_resolve_image_source`'s `drive:` path in `content.py`) were consolidated into one shared `check_drive_image_metadata` helper reading both `imageMediaMetadata` and Drive's own `size` field, replacing what had been the same `check_dimensions`-only pattern duplicated across both files. PR #580's own QA round 1 caught that `rewrite_too_large_error` — the fallback for `uri`-sourced images, which skip pre-validation entirely — still only named the 25-megapixel limit, even though a byte-size-caused rejection could now reach it too; since Google's raw error text doesn't say which limit was actually hit and this call site never fetched the bytes to check, the message was made limit-agnostic (names both ceilings) rather than guessing which one applies. `insert_inline_image`'s `drive_file_id` path, `insert_local_images`' `local_path` entries, and `_resolve_image_source`'s `drive:`/local-path branches (`content.py`) all gained an opt-in `auto_downscale` param (default `False`, fail-fast with the clear error) wired to this module — a `drive_file_id`/`drive:` source that gets downscaled creates a new `" (resized)"`-suffixed copy alongside the original via `downscale_drive_file` (the original file is never mutated), while a local-path source just uploads the resized bytes directly via `upload_and_share_image` instead of the original file, since there's no pre-existing Drive artifact to avoid colliding with. Deliberately out of scope: a bare `http(s)://` image source (either `insert_inline_image`'s own `uri` param or a markdown/HTML `![alt](http://...)`/`<img src="http://...">`) — pre-validating or auto-downscaling it would mean fetching arbitrary external content just to check it, and re-hosting a resized copy somewhere Google can fetch it from is a bigger behavior change than this fix warrants. That source kind instead gets `rewrite_too_large_error`'s fallback: Google's own "too large" `HttpError` message is caught and rewritten with the same limit/size explanation once the embed actually fails, rather than staying opaque.
  - `docs/anchors.py` — `resolve_heading_anchor`, the pure slug-matching logic behind the anchor-resolution pass above. Tries GitHub's non-collapsing hyphen convention (hand-rolled — no known Python package reproduces it) and GitLab's collapsing convention (delegated to `python-markdown`'s own `toc` extension `slugify`, already a project dependency, confirmed live to collapse hyphens the same way) against the document's full heading list, with GitHub/GitLab-style numeric `-1`/`-2` duplicate-heading disambiguation applied before matching; falls back to normalized word-token comparison for a slug that doesn't exactly match either scheme. Deliberately does not try to detect which generator produced a given anchor up front — see the design doc for why. Has an inline `TODO(#409 follow-up)` flagging the cascading try-each-scheme approach as a first pass, not the most precise/efficient possible mechanism. The same QA round (PR #453) found the fuzzy fallback could silently resolve to the *wrong* heading: it unconditionally stripped a trailing `-<digits>` from the anchor before comparing, even when those digits were genuine heading wording rather than a dedup suffix, and its match loop returned the *first* heading with matching normalized tokens with no regard for which duplicate a stripped suffix actually pointed at — directly contradicting the feature's own "a wrong link is worse than no link" design goal. **Startup / auth** (`spreadsheet_lifespan`): FastMCP lifespan context manager that authenticates on server start and injects a `SpreadsheetContext` (holding `sheets_service`, `drive_service`, `docs_service`, `calendar_service`, and `activity_service`) into every tool call via `ctx.request_context.lifespan_context`.

The project philosophy is to be as powerful and flexible as possible by default, while giving security-conscious users the configuration knobs to lock things down. Two mechanisms reflect this:

- **Auth** (`AUTH_METHOD`): out of the box the waterfall tries everything so the server just works; setting `AUTH_METHOD` restricts it to exactly one method with no fallback.
- **Tool surface** (`ENABLED_TOOLS` / `--include-tools`): by default all tools are registered; setting `ENABLED_TOOLS` to a comma-separated list of function names limits the server to exactly that subset. This lets operators expose only the tools their users need.

By default (`AUTH_METHOD` unset), auth falls through in order: OAuth (`CREDENTIALS_PATH`/`TOKEN_PATH`) → service account (`CREDENTIALS_CONFIG` or `SERVICE_ACCOUNT_PATH`) → Application Default Credentials. OAuth is tried first because it authenticates as the user (full personal Drive access); service account is a fallback for headless/server deployments.

Set `AUTH_METHOD` to pin a specific method with no fallback — removes ambiguity for security audits, CI, or testing a tool's behavior under a known credential type:
- `AUTH_METHOD=oauth` — OAuth only; fails fast if credentials are missing
- `AUTH_METHOD=service_account` — service account only; requires `CREDENTIALS_CONFIG` or `SERVICE_ACCOUNT_PATH`
- `AUTH_METHOD=adc` — ADC only

**Logging** (`DEBUG_LEVEL` env var): when set, configures the `mcp_gee_sweet` package logger and `uvicorn.access` logger to the given level (`DEBUG`, `INFO`, `WARNING`, `ERROR`). The `_timed` wrapper in `server.py` emits one `INFO` line per tool call to `mcp_gee_sweet.access` — format: `"IP" "UA" "TOOL name" status elapsed`. IP/UA come from `ctx.request_context` in SSE mode; fall back to `-` in stdio. `LOG_FILE` and `ACCESS_LOG_FILE` env vars write logs to file (required for stdio where stderr is dropped by the host). Runtime config lives in `src/mcp_gee_sweet/.env` (gitignored); template at `src/mcp_gee_sweet/.env.template`.

**Tool registration** (`tool` decorator wrapper): A custom `@tool()` decorator wraps `@mcp.tool()`. It checks `ENABLED_TOOLS` (set via `ENABLED_TOOLS` env var or `--include-tools` CLI arg) and skips registration for any tool not in the allowlist. This is how tool filtering works — tools simply aren't registered with FastMCP rather than being conditionally hidden.

**Async execution** (`execute_in_thread` + `thread_http`, in `http_transport.py`): every `@tool()`-registered function is `async def`, and `_timed`'s wrapper is unconditionally `async def wrapper(...): return await func(...)` — so **any new tool must be `async def`**, even one with no Google API calls (see `tools/cache.py`'s `get_cache_ttl`/`set_cache_ttl`/`refresh_cache` for an example with an empty `await`-free body; a plain `def` there raises `TypeError` at call time since `await`ing a sync return value fails — `test_server.py::TestAllToolsAreAsync` guards against this recurring). Every `.execute()` call is wrapped `await execute_in_thread(chain.execute, service)` (`http_transport.py`, re-exported from `auth.py` for existing imports) — **do not** write `asyncio.to_thread(chain.execute, http=thread_http(service))` directly: `thread_http(service)` as an eagerly-evaluated kwarg resolves on the event-loop thread before the worker thread starts, so concurrent calls end up sharing one transport across threads (a real, live-reproduced bug, fixed in #183's follow-up round — see the decision doc). `execute_in_thread` defers the `thread_http()` call into the thread itself via a lambda. `thread_http()` hands each worker thread its own `AuthorizedHttp` transport built from the shared credentials, since the lifespan-scoped `sheets_service`/`drive_service`/etc. objects each carry one `httplib2` transport that isn't safe for concurrent use across threads. Six multi-call tools (`sync_folder`, `get_multiple_sheet_data`, `get_multiple_spreadsheet_summary`, `import_csv_to_sheet`, `share_spreadsheet`, `share_file`) parallelize their per-item work via `asyncio.gather(..., return_exceptions=True)` instead of looping serially. `cache.py`'s SQLite I/O deliberately stays synchronous, not `to_thread`-wrapped — see the comment in `cache.py::_open()`; the module's two Google-API-calling helpers (`get_modified_time`, `fetch_sheets`) are `async def` and do use `execute_in_thread` for their own `.execute()` calls. `_BaseCache.snapshot_epoch()`/`store(..., epoch=...)` guard against a `refresh_cache()` call landing mid-fetch and having its invalidation silently overwritten — only wired up for `SheetStructureCache`/`SheetDataCache` so far. Full rationale: `docs/decisions/decision-async-tool-execution.md`. When unit-testing genuine cross-thread concurrency (not just correctness) with a `threading.Barrier` or similar, the block must live inside the mocked `.execute()` call, not `.list()`/`.create()`/etc. — those are evaluated eagerly on the event-loop thread while building the call chain, before `execute_in_thread` ever hands off to a worker thread, so blocking there freezes the single-threaded event loop instead of proving concurrency (see `tests/drive/test_transfer.py::TestSyncFolderRecursive::test_recursive_sibling_subfolders_descend_concurrently`). `download_folder`/`sync_folder` (#316/#319) added `ctx.report_progress()` calls from inside each item's own per-item coroutine so updates stream as concurrent transfers complete rather than arriving in one burst after the whole `gather` resolves — any future tool adding progress reporting to a gather-based batch (tracked for the remaining `asyncio.gather` tools in #355) must wrap that `report_progress` call in its own try/except: it's awaited *after* the item's real work already succeeded or failed, with no other guard around it, so a report_progress exception (e.g. a dropped client session) would otherwise propagate out, get caught by the outer `gather(..., return_exceptions=True)`, and overwrite an already-successful result with a spurious failure — confirmed live and fixed in PR #351's review round.

**A1 notation helpers**: `_parse_a1_notation`, `_column_index_to_letter`, and `_letter_to_column_index` convert between A1 ranges and the 0-based row/column indices the Sheets batchUpdate API requires. The Sheets values API uses A1 notation directly; batchUpdate requires numeric indices — keep that distinction in mind when adding new tools.

**Docs API indices are UTF-16 code units, not Python code points**: every `startIndex`/`endIndex` in the Docs API counts UTF-16 code units — an astral-plane character (most emoji, some CJK/math symbols) is one Python `str` character but a 2-unit surrogate pair. `content.py`'s `find_in_doc` and `indices.py`'s `_collect_doc_paragraphs` account for this via `utf16_len`. `emitter.py`'s offset math (table positions, paragraph-style ranges, inline run-style ranges) does not — it derives offsets from plain `len()`/`enumerate()`, a confirmed-pattern bug tracked in #358. Any new code deriving a Docs API index from Python string length needs `utf16_len`-style accounting instead of raw `len()`.

**Sheets API `TextFormatRun.startIndex` is also UTF-16 code units** (confirmed via the API reference, same gotcha class as the Docs API note above): `update_cells` (`tools/sheets/data.py`) accepts a rich-text cell as a list of `{"text": str, "hyperlink": str | None}` run dicts for partial (rich-text) hyperlinks within a single cell (issue #89) — `_build_rich_text_cell` computes each run's `startIndex` via `_utf16_len` (`sheets/helpers.py`, which delegates to `docs/indices.py`'s `utf16_len` rather than duplicating its per-character logic), not `len()`, so a run following an astral-plane character (emoji, some CJK/math symbols) lands at the correct offset. A `data` array with no rich-text cells still goes through the original whole-range `values().update()` USER_ENTERED path unchanged. A `data` array that mixes plain and rich-text cells does **not** — an earlier version wrote the whole range via `values().update()` with rich-text positions blanked to `""`, relying on the second `batchUpdate` pass (the one that writes the rich-text `updateCells` requests) to overwrite those blanks back; if that second call failed, the blank was never restored and the rich-text cells' prior content was lost (live-confirmed via TC-W34 review, PR #380). The fixed version writes only the actual plain-cell positions via a per-cell `values().batchUpdate()` instead, so the two passes never touch each other's cells and a failure in one can't corrupt the other's data. Because they're now two independent API calls whenever both plain and rich-text cells are present, the tool returns `{"values_update": ..., "rich_text_update": ...}` in that case rather than silently dropping one result — only a call with just one kind of cell returns that single call's raw response.

**MCP resources**: Two resources are registered — `server://auth-status` (active auth method and Drive capability limits) and `spreadsheet://{spreadsheet_id}/info` (sheet list and grid properties). Neither takes a `ctx` argument the way tools do, so both fetch it explicitly via `mcp.get_context().request_context.lifespan_context` — `FastMCP` has no `get_lifespan_context()` method (confirmed absent as far back as `mcp==1.27.1`, so this was never a regression from #350's SDK bump; it was a pre-existing bug invisible to unit tests since `TestAuthStatusResource` only exercised `_auth_status_json()` directly, never the resource function itself — fixed in #363). `get_context()` returns a `Context` whose `.request_context.lifespan_context` is the same `SpreadsheetContext` tools reach via `ctx.request_context.lifespan_context`.

**`batch_update` tool**: This is a passthrough to the Sheets `spreadsheets().batchUpdate()` endpoint and accepts raw request objects. It's the escape hatch for any operation not covered by the named tools (formatting, conditional formatting, dimension properties, etc.).

## Development workflow

**MCP restart**: After `docker compose restart mcp-gee-sweet`, Claude Code does not automatically reconnect to the SSE server — you must restart Claude Code too to re-establish the connection. The same staleness applies to a team role's own stdio `mcp-gee-sweet-<name>` server (confirmed while fixing #336): it's a single long-running subprocess that imports this package's code once at session start, so editing `.py` files afterward does **not** get picked up by that already-running process — a live tool call (e.g. `create_doc`) made after a mid-session edit silently exercises the *pre-edit* code, which can look exactly like a real live-rendering bug (it reproduced one that had already been fixed on disk). `uv run python3 -c "..."` invocations in the same worktree are unaffected (fresh interpreter, fresh import each time) and are the reliable way to live-verify a same-session code change against the real API without restarting the whole session — reuse `mcp_gee_sweet.auth._oauth_creds()` plus `googleapiclient.discovery.build(...)` directly (the same construction `spreadsheet_lifespan` uses) to get a real `docs`/`drive` service in a throwaway script. This is also the only way to inspect fields no tool surfaces, like `documents().get()`'s raw `paragraph.bullet`/`lists` — what actually pinned down PR #432's live nesting behavior.

**Generated tool docs**: `docs/tools.md` and the "Tool filtering" section of `docs/configuration.md` are generated by `scripts/gen_tool_docs.py` from the tool source (names, signatures, docstrings) — do not hand-edit the tool tables in either file. The script is wired into `.pre-commit-config.yaml` and runs whenever a file under `src/mcp_gee_sweet/tools/` or either generated doc changes; it fails the commit if a tool has no docstring, if a tool doesn't match any section in the script's `SECTIONS` config, or if a `SUBSETS` entry references a renamed/removed tool name. Run it manually with `uv run python scripts/gen_tool_docs.py`.

**PR creation**: open PRs ready-for-review (`gh pr create`, no `--draft`), not as drafts — draft should be an explicit, stated exception (e.g. genuinely incomplete work you want visible early), not the default. `gh pr merge --admin` refuses a draft PR outright (`merge-pr.md` now handles it by readying first), so an unnecessary draft is pure friction at merge time with no upside.

**Regression vs. pre-existing bug after a dependency bump**: when a bug report asks "is this a regression from the recent SDK bump" (e.g. issue #363 against #350's `mcp>=1.28.1` change), don't answer from memory or by reading changelogs alone — install the *old* pinned version in a scratch venv and check the specific API surface directly against it (e.g. `python3 -m venv /tmp/x && ./x/bin/pip install "mcp==1.27.1" && ./x/bin/python -c "from mcp.server.fastmcp import FastMCP; print(hasattr(FastMCP, 'get_lifespan_context'))"`). Confirmed in #363: `FastMCP.get_lifespan_context()` looked like it could've been removed by the bump, but it never existed even at `1.27.1` — the scratch-venv check settled the question in seconds instead of guessing from a diff.

**Verify a ticket's API premise live before implementing, not after.** An issue's ask can rest on an unverified assumption that a specific Google API field or request is settable, just because that field appears in the API's discovery schema — a schema documents read-only fields as ordinary properties, so presence alone doesn't mean writable. Before building a feature around a Google API capability not already confirmed live elsewhere in this codebase, run the same scratch-script check described above under "MCP restart" (`uv run python3 -c "..."` with `mcp_gee_sweet.auth._oauth_creds()` + `googleapiclient.discovery.build(...)`) against the live discovery document *first* — read the target field's own `description` for a "read-only" note, and confirm at least one request type in the schema actually references it for writing — before writing any implementation. Confirmed the hard way on issue #404/PR #471: `style_doc_range` shipped a full `tab_stops` implementation, unit tests, and QA test cases before QA's live round hit `HttpError 400 ... "Unallowed field: tabStops"`. A follow-up discovery-schema check took two minutes and confirmed `ParagraphStyle.tabStops`'s own description reads "This property is read-only," with no request type anywhere in the Docs API able to set it — the same check, run before implementation instead of after QA sent it back, would have caught this without costing a full dev+QA cycle. Closed as infeasible rather than fixed (issue #404, PR #471, follow-up #473 filed for the documented workaround).

**Procedural feedback → the governing command file, not memory.** If the human's feedback corrects or refines a repeatable team-workflow step that a `.claude/team-roles/*.md` or `.claude/commands/*.md` file already governs (or should) — as opposed to project context, an external-system pointer, or a one-off judgment call specific to the current conversation — that's a command decision (`.claude/commands/retro.md`'s disposition), not a memory entry: edit the file directly, through Bob's prompt-QA gate (`.claude/team-roles/bob.md`), rather than trusting memory to carry it. A memory-only fix is retrieved heuristically and competes with whatever the loaded prompt already says instead of reliably overriding it — confirmed the hard way on PR #456: two separate memory-only fixes for QA's `/mcp reconnect`+`/code-review` batching (`qa.md` step 2) each got silently re-broken by a later session before the rule was hard-coded into `qa-kickoff.md` instead. Memory is still the right home for what's genuinely outside the team's tracked process — it just isn't a substitute for a rule a command file is meant to enforce every time.
