# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Run locally from the cloned repo:
```bash
uv run mcp-gee-sweet
uv run mcp-gee-sweet --transport sse   # SSE instead of stdio
```

Build and publish:
```bash
uv build       # produces dist/*.whl
uv sync        # install deps from uv.lock
```

Docker:
```bash
docker build -t mcp-gee-sweet .
docker run --rm -p 8000:8000 \
  -e CREDENTIALS_CONFIG=<base64> \
  -e DRIVE_FOLDER_ID=<id> \
  mcp-gee-sweet
```

Tests live in `tests/` and can be run with `uv run pytest`.

## Architecture

Logic is split across `src/mcp_gee_sweet/`: `server.py` (MCP setup, tool decorator, resources), `auth.py` (lifespan, `SpreadsheetContext`), and `tools/` (domain-based layout).

Each entry below says what a module owns and the invariants a future edit could break. The per-PR history behind them (review rounds, reversed approaches, the incident behind each rule) is in [`docs/design/module-history.md`](docs/design/module-history.md), linked from each entry as *History*. Read a module's history before changing its behavior. Record new history in a design or decision doc, not here.

- `tools/drive/transfer.py` — upload/download/sync/export/revisions. [History](docs/design/module-history.md#toolsdrivetransferpy). Invariants:
  - `_upload_local_file` (the core of `upload_local_file`) stays module-level: `docs/images.py` imports it cross-package, the same way `docs/content.py` imports `_SA_QUOTA_ERROR`. A `storageQuotaExceeded` error renders as `_SA_QUOTA_ERROR` at every site.
  - **Two conversion mechanisms; don't conflate them.** Drive *native import conversion* uploads with the source mimeType and sets the target Workspace mimeType in metadata (`_CONVERT_MIME`: CSV/XLSX→Sheets, DOCX/MD/HTML→Docs, PPTX→Slides). It backs `upload_local_file(convert=)`, `upload_local_folder(convert=)`, `sync_folder(convert_markdown=)`, and `upload_file(convert_to_doc=)` (raw content, always a Doc; shares `_GOOGLE_DOC_MIME`). `docs/content.py`'s `create_doc_from_file` is different: it parses locally and rebuilds via Docs API requests.
  - **Converted `.md` Docs** keep the `.md` name in Drive and are recognized on every later sync by a Drive `properties` marker stamped at creation through `_convert_properties` (by both `_sync_level` and `_upload_local_file(convert=True)`), regardless of the current call's flags. Values must fit Drive's 124-byte per-property cap: `_CONVERT_MARKDOWN_SOURCE_PROP` holds the raw name when it fits, else `_CONVERT_SOURCE_PROP` holds a `sha256:` digest (a digest-marked Doc stops matching if renamed; see `docs/known-limitations.md`). Classify through `_converted_md_source_name`/`_is_converted_md_entry`, recomputed from the resource each time; never cache the classification on a `drive_map` entry. There is no reverse conversion: a drive-only or drive-newer converted Doc is a `conflict` (message via `_NO_REVERSE_CONVERSION_CLAUSE`), except `direction='upload'`, which reports a plain `skip`.
  - **Name collisions** in `drive_map` (any duplicate name, any type) go through the plan as a `"collision"` action: `conflict` under `dry_run`, a `failed` entry (`kind: "collision_fail"`) on execution. Never write to `failed` from the `drive_map`-building loop.
  - **`dry_run`** never reports failures and never hashes. It leaves `uploaded`/`downloaded`/`skipped`/`conflicts`/`failed` empty; `actions` alone is the complete preview (duplicating it tripped the response cap).
  - **`modifiedTime` stamping.** Every upload stamps `modifiedTime` from the local mtime in `create()`. A converted upload also needs a metadata-only `update()` afterward, because Drive's asynchronous conversion overwrites the create-time value (the doubled latency is accepted). If that restamp fails after `create()` succeeded, report the created file's ID via `_restamp_failure_result` (`{"error", "fileId"}`); `_sync_level`, `upload_local_file`, and `upload_local_folder` must carry `fileId` into `failed` and treat that result as cache-dirtying. `_upload_local_file` catches broadly and returns `{"error": ...}`, since the tool has no try/except of its own.
  - **`sync_folder` comparison** for a name on both sides: mtime diff first, against `_SYNC_MTIME_TOLERANCE`. Within tolerance but a different `size` (non-Workspace files only) is a `conflict` for every direction: recency is unknown, so never auto-transfer. `use_checksum=True` hashes every both-sides pair that has a Drive `md5Checksum` (after the plan loop, concurrently, capped by `_SYNC_HASH_CONCURRENCY`, filling placeholder steps from `_mtime_step`): a match is in sync, a within-tolerance mismatch is a `conflict` (`_diverged_same_mtime_step`), and a mismatch outside tolerance falls through to the mtime logic. Under `dry_run` those reasons end in `(checksum not verified in dry_run)`. A local file that can't be read or stat'd becomes a `"local_read_fail"` plan action, never an uncaught raise. Workspace and converted files have no `md5Checksum`/`size` and always compare by mtime alone.
  - **`upload_local_folder`** routes each file through `_upload_local_file(skip_if_exists=False)` but keeps its own single bulk `list()` for `skip_if_exists` (name match; name plus target mimeType when `convert=True`), so existence is checked once. An unsupported extension under `convert` lands in `failed`, never uploads as-is.
  - **`sync_folder(result_local_path=)`** is its response-cap bypass (`local_path` already means the sync directory). It's rejected with `ValueError` before any API call if it resolves inside `local_path`, where the manifest would be synced up. `enforce_response_size_cap(local_path_param=...)` names the right parameter in the cap error.

`__init__.py` loads `src/mcp_gee_sweet/.env` via `python-dotenv` before importing `server`, so env vars from that file are in `os.environ` by the time any module-level `os.environ.get()` runs. Priority: real env var > `.env` > default.

**Startup / auth** (`spreadsheet_lifespan`): MCPServer lifespan context manager that authenticates on server start and injects a `SpreadsheetContext` (holding `sheets_service`, `drive_service`, `docs_service`, `calendar_service`, and `activity_service`) into every tool call via `ctx.request_context.lifespan_context`. It also stamps the same `SpreadsheetContext` into a module-level `auth._lifespan_context`, readable via `auth.get_lifespan_context()` — this is what `server.py`'s static `server://auth-status` resource reads instead of going through Context (see the MCP resources note below).

**The lifespan runs once per connection under SSE, not once per process.** mcp v2's `Server.run` enters `spreadsheet_lifespan` for every SSE connection; stdio has exactly one. So per-connection auth outcomes belong on the `SpreadsheetContext` it yields, never in a module global that a later connection's lifespan can overwrite or reset. PR #828 (#811) round 1 kept its degraded-start message in a global, and QA caught a second connection clearing the message the first still relied on. Genuinely process-wide decisions (e.g. "don't retry the blocking consent flow") are the exception, and should say so in a comment.

**No usable OAuth token (#811):** under stdio the server never runs the browser consent (stdout is the JSON-RPC channel). `AUTH_METHOD=oauth`, or the waterfall with no service account/ADC fallback, starts *degraded*: the yielded context has every service `None` and `unauthorized_message` set, and `server.py`'s `_timed` wrapper raises that message before any tool body runs. It raises rather than returns, because a `{"error": ...}` dict would fail a list-typed tool's output schema. Under SSE the consent runs with its prompt on stderr and an `OAUTH_CONSENT_TIMEOUT_SECONDS` bound. Any failure degrades that connection, and consent is never retried in the process, since the wait is synchronous and blocks every connection. The recovery path users are pointed at is the `mcp-gee-sweet auth` subcommand (`auth.run_auth_command`, argv parsing in `server._auth_main`). `scripts/oauth_setup.py` is only a QA wrapper over the same `run_consent_flow`/`write_token_json` (0600) helpers.

**CodeQL flags logging any value whose name looks like a secret.** `py/clear-text-logging-sensitive-data` is a *high* alert that blocks merge. It keys on names, so logging a raw `OAUTH_CONSENT_TIMEOUT_SECONDS` value (an integer) tripped it on PR #828 after QA had already passed. Don't interpolate the value of an `OAUTH_*`/`*TOKEN*`/`*SECRET*`/`*PASSWORD*`-named env var or variable into a log message; name the setting without echoing it.

The project philosophy is to be as powerful and flexible as possible by default, while giving security-conscious users the configuration knobs to lock things down. Two mechanisms reflect this:

- **Auth** (`AUTH_METHOD`): out of the box the waterfall tries everything so the server just works; setting `AUTH_METHOD` restricts it to exactly one method with no fallback.
- **Tool surface** (`ENABLED_TOOLS` / `--include-tools`): by default all tools are registered; setting `ENABLED_TOOLS` to a comma-separated list of function names limits the server to exactly that subset. This lets operators expose only the tools their users need.

By default (`AUTH_METHOD` unset), auth falls through in order: OAuth (`CREDENTIALS_PATH`/`TOKEN_PATH`) → service account (`CREDENTIALS_CONFIG` or `SERVICE_ACCOUNT_PATH`) → Application Default Credentials. OAuth is tried first because it authenticates as the user (full personal Drive access); service account is a fallback for headless/server deployments.

Set `AUTH_METHOD` to pin a specific method with no fallback — removes ambiguity for security audits, CI, or testing a tool's behavior under a known credential type:
- `AUTH_METHOD=oauth` — OAuth only; fails fast if the OAuth client JSON is missing, and starts degraded (see above) if there is no usable token
- `AUTH_METHOD=service_account` — service account only; requires `CREDENTIALS_CONFIG` or `SERVICE_ACCOUNT_PATH`
- `AUTH_METHOD=adc` — ADC only

**Logging** (`DEBUG_LEVEL` env var): when set, configures the `mcp_gee_sweet` package logger and `uvicorn.access` logger to the given level (`DEBUG`, `INFO`, `WARNING`, `ERROR`). The `_timed` wrapper in `server.py` emits one `INFO` line per tool call to `mcp_gee_sweet.access` — format: `"IP" "UA" "TOOL name" status elapsed`. IP/UA come from `ctx.request_context` in SSE mode; fall back to `-` in stdio. `LOG_FILE` and `ACCESS_LOG_FILE` env vars write logs to file (required for stdio where stderr is dropped by the host). Runtime config lives in `src/mcp_gee_sweet/.env` (gitignored); template at `src/mcp_gee_sweet/.env.template`.

**Tool registration** (`tool` decorator wrapper): A custom `@tool()` decorator wraps `@mcp.tool()`. It checks `ENABLED_TOOLS` (set via `ENABLED_TOOLS` env var or `--include-tools` CLI arg) and skips registration for any tool not in the allowlist. This is how tool filtering works — tools simply aren't registered with MCPServer rather than being conditionally hidden.

**Async execution** (`execute_in_thread` + `thread_http`, in `http_transport.py`; full rationale in `docs/decisions/decision-async-tool-execution.md`, [History](docs/design/module-history.md#async-execution)):
- Every `@tool()` function must be `async def`, even one with no API calls: `_timed` awaits it, so a plain `def` raises `TypeError` (`test_server.py::TestAllToolsAreAsync` guards this).
- Wrap every `.execute()` as `await execute_in_thread(chain.execute, service)`. Never write `asyncio.to_thread(chain.execute, http=thread_http(service))`: the kwarg is evaluated on the event-loop thread, so concurrent calls share one non-thread-safe `httplib2` transport.
- Six multi-call tools (`sync_folder`, `get_multiple_sheet_data`, `get_multiple_spreadsheet_summary`, `import_csv_to_sheet`, `share_spreadsheet`, `share_file`) fan out with `asyncio.gather(..., return_exceptions=True)`.
- A `ctx.report_progress()` call inside a gathered per-item coroutine must be wrapped in its own try/except, or a dropped client session turns an already-successful item into a failure.
- `cache.py`'s SQLite I/O stays synchronous on purpose (see `cache.py::_open()`). `_BaseCache.snapshot_epoch()`/`store(..., epoch=...)` stop a mid-fetch `refresh_cache()` from being overwritten, per key (`SheetStructureCache`, `SheetDataCache`, `DriveFolderCache`). Size-bounded caches share `_get_sized`/`_store_sized`.
- To unit-test real cross-thread concurrency, put the barrier inside the mocked `.execute()`, not `.list()`/`.create()`, which run on the event-loop thread (see `tests/drive/test_transfer.py::TestSyncFolderRecursive::test_recursive_sibling_subfolders_descend_concurrently`).

**Two Google API clients**: The server builds both a Sheets client (`sheets/v4`) and a Drive client (`drive/v3`). Most tools use only the Sheets client; `list_spreadsheets`, `create_spreadsheet`, `share_spreadsheet`, and `list_folders` use Drive. `create_spreadsheet` uses Drive to create the file (so it can place it in a folder), not the Sheets API.

**A1 notation helpers**: `_parse_a1_notation`, `_column_index_to_letter`, and `_letter_to_column_index` convert between A1 ranges and the 0-based row/column indices the Sheets batchUpdate API requires. The Sheets values API uses A1 notation directly; batchUpdate requires numeric indices — keep that distinction in mind when adding new tools.

**Docs API indices are UTF-16 code units, not Python code points**: every `startIndex`/`endIndex` in the Docs API counts UTF-16 code units — an astral-plane character (most emoji, some CJK/math symbols) is one Python `str` character but a 2-unit surrogate pair. `content.py`'s `find_in_doc` and `indices.py`'s `_collect_doc_paragraphs` account for this via `utf16_len`. `emitter.py`'s offset math (table positions, paragraph-style ranges, inline run-style ranges) does not — it derives offsets from plain `len()`/`enumerate()`, a confirmed-pattern bug tracked in #358. Any new code deriving a Docs API index from Python string length needs `utf16_len`-style accounting instead of raw `len()`.

**Sheets API `TextFormatRun.startIndex` is also UTF-16 code units.** `update_cells` (`tools/sheets/data.py`) accepts a rich-text cell as a list of `{"text", "hyperlink"}` runs; `_build_rich_text_cell` computes offsets with `_utf16_len` (`sheets/helpers.py`, delegating to `docs/indices.py`). A `data` array with only plain cells uses one `values().update()`. A mixed array writes plain cells by position via `values().batchUpdate()` and rich-text cells via a separate `batchUpdate`, so the two passes never touch each other's cells, and returns `{"values_update", "rich_text_update"}`. Never blank rich-text positions in the values write and rely on the second call to fill them: if it fails, the data is lost. [History](docs/design/module-history.md#sheets-api-textformatrunstartindex-is-also-utf-16-code-units).

**MCP resources**: `server://auth-status` (active auth method and Drive capability limits) and `spreadsheet://{spreadsheet_id}/info` (sheet list and grid properties). mcp v2 has no `get_context()` and can't inject Context into a *static* resource. So the template resource `get_spreadsheet_info` takes `ctx: Context` like a tool, while the static `get_auth_status` reads the process-wide `auth.get_lifespan_context()` singleton. See `docs/decisions/decision-mcp-v2-resource-context-access.md`. [History](docs/design/module-history.md#mcp-resources).

**`batch_update` tool**: This is a passthrough to the Sheets `spreadsheets().batchUpdate()` endpoint and accepts raw request objects. It's the escape hatch for any operation not covered by the named tools (formatting, conditional formatting, dimension properties, etc.).

## Development workflow

**MCP restart**: after `docker compose restart mcp-gee-sweet`, restart Claude Code too; it doesn't reconnect to the SSE server. A team role's stdio `mcp-gee-sweet-<name>` server imports the package once at session start, so a live tool call after a mid-session edit runs the *pre-edit* code, which can look exactly like a real bug. To live-verify a same-session change, use a fresh interpreter: `uv run python3 -c "..."` with `mcp_gee_sweet.auth._oauth_creds()` plus `googleapiclient.discovery.build(...)`. That's also the only way to inspect raw fields no tool surfaces (e.g. `paragraph.bullet`, `lists`). [History](docs/design/module-history.md#mcp-restart).

**Generated tool docs**: `docs/tools.md` and the "Tool filtering" section of `docs/configuration.md` are generated by `scripts/gen_tool_docs.py` from the tool source (names, signatures, docstrings) — do not hand-edit the tool tables in either file. The script is wired into `.pre-commit-config.yaml` and runs whenever a file under `src/mcp_gee_sweet/tools/` or either generated doc changes; it fails the commit if a tool has no docstring, if a tool doesn't match any section in the script's `SECTIONS` config, or if a `SUBSETS` entry references a renamed/removed tool name. Run it manually with `uv run python scripts/gen_tool_docs.py`.

**PR creation**: open PRs ready-for-review (`gh pr create`, no `--draft`), not as drafts — draft should be an explicit, stated exception (e.g. genuinely incomplete work you want visible early), not the default. `gh pr merge --admin` refuses a draft PR outright (`merge-pr.md` now handles it by readying first), so an unnecessary draft is pure friction at merge time with no upside.

**Regression vs. pre-existing bug after a dependency bump**: don't answer from memory or changelogs. Install the old pinned version in a scratch venv and check the API surface directly, e.g. `python3 -m venv /tmp/x && /tmp/x/bin/pip install "mcp==1.27.1" && /tmp/x/bin/python -c "...hasattr(...)"`. [History](docs/design/module-history.md#regression-vs-pre-existing-bug-after-a-dependency-bump).

**Verify a ticket's API premise live before implementing, not after.** A field in a Google API discovery schema isn't necessarily writable; the schema lists read-only fields as ordinary properties. Before building on a capability not already confirmed live in this codebase, check the live discovery document with the scratch-script approach above: read the field's own `description` for a "read-only" note, and confirm some request type actually writes it. (`ParagraphStyle.tabStops` cost a full dev+QA cycle this way; #404.) [History](docs/design/module-history.md#verify-a-tickets-api-premise-live-before-implementing-not-after).

**Procedural feedback → the governing command file, not memory.** If the human's feedback corrects a repeatable team-workflow step that a `.claude/team-roles/*.md` or `.claude/commands/*.md` file governs (or should), edit that file, through Bob's prompt-QA gate (`.claude/team-roles/bob.md`); `.claude/commands/retro.md` treats this as a command decision. A memory-only fix is retrieved heuristically and loses to whatever the loaded prompt says. Memory is still right for project context, external pointers, and one-off judgment calls. [History](docs/design/module-history.md#procedural-feedback--the-governing-command-file-not-memory).
