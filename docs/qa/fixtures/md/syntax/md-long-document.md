## 1. Problem

Users repeat the same searches every day. Today they retype the query and
re-apply filters each time, which takes about 40 seconds per search based on
session recordings.

## 2. Goals and non-goals

### Goals

- Let a user save a search (query + filters + sort) with a name
- Show saved searches in the sidebar
- Notify the user when new results match a saved search

### Non-goals

- Sharing saved searches with other users (v2)
- Saved searches on mobile (v2)

## 3. User stories

1. As an analyst, I want to save a search so that I can rerun it in one click.
2. As an analyst, I want to rename or delete a saved search.
3. As a manager, I want a daily email digest of new matches.

## 4. Requirements

### 4.1 Functional

| ID | Requirement | Priority |
|:---|:------------|:--------:|
| F1 | Save the current search with a name (max 80 chars) | P0 |
| F2 | List saved searches, most recent first | P0 |
| F3 | Rename and delete a saved search | P1 |
| F4 | Daily digest email for new matches | P2 |

### 4.2 Non-functional

- Saving a search must complete in under **200 ms** (p95)
- A user can have at most 50 saved searches

The client calls a new endpoint:

```http

The response includes the new search's `id` and `created_at`.

# fastqueue

A small, dependency-free job queue for Python services.

[![Build](https://img.shields.io/badge/build-passing-brightgreen)](https://example.com/ci)

## Features

- In-process or Redis-backed storage
- Retries with exponential backoff
- Scheduled jobs (`run_at=`)
- Type-annotated API

## Installation

```bash
pip install fastqueue
```

For Redis support:

```bash
pip install "fastqueue[redis]"
```

## Quick start

```python
from fastqueue import Queue

q = Queue()

@q.job(retries=3)
def send_email(to: str, subject: str) -> None:
    ...

send_email.delay("user@example.com", "Welcome!")
q.run_worker()
```

## Configuration

| Option | Default | Description |
|--------|---------|-------------|
| `backend` | `"memory"` | `"memory"` or `"redis"` |
| `redis_url` | `None` | Required when `backend="redis"` |
| `max_retries` | `5` | Upper bound for any job |
| `poll_interval` | `0.5` | Seconds between polls |

## Usage notes

1. Jobs must be importable by the worker process.
2. Arguments must be JSON-serializable.
3. Use `q.job(timeout=...)` for long-running work:
   ```python
   @q.job(timeout=300)
   def rebuild_index(): ...
   ```
4. Call `q.shutdown()` on exit to flush pending acks.

> **Note:** the in-memory backend loses jobs when the process exits. Use Redis
> in production.

## Contributing

PRs are welcome. Please run `make test` and `make lint` before opening one, and
see [CONTRIBUTING.md](https://example.com/contributing) for details.

# How to Set Up a Local Development Environment

This guide walks you through setting up the service on macOS or Linux. It takes
about 15 minutes.

## Prerequisites

- Python 3.12 or newer
- Docker Desktop (or Docker Engine on Linux)
- Access to the team's GitHub organization

## Steps

1. **Clone the repository.**

   ```bash
   git clone https://github.com/example/service.git
   cd service
   ```

2. **Create a virtual environment and install dependencies.**

   ```bash
   python3 -m venv .venv
   source .venv/bin/activate
   pip install -r requirements-dev.txt
   ```

3. **Start the backing services.** This starts Postgres and Redis in containers:

   ```bash
   docker compose up -d db redis
   ```

   Wait until both containers report `healthy`:

   ```bash
   docker compose ps
   ```

4. **Configure your environment.**
   - Copy `.env.example` to `.env`
   - Set `DATABASE_URL` to `postgresql://dev:dev@localhost:5432/service`
   - Leave `FEATURE_FLAGS` empty unless you need a specific flag

5. **Run the migrations and start the server.**

   ```bash
   make migrate
   make run
   ```

   The server listens on <http://localhost:8000>.

## Troubleshooting

**Port 5432 is already in use.** Another Postgres is running. Stop it, or change
the port mapping in `docker-compose.yml`.

**`pip install` fails on `psycopg`.** Install the Postgres client headers:

- macOS: `brew install libpq`
- Debian/Ubuntu: `sudo apt install libpq-dev`

> **Tip:** run `make doctor` to check every prerequisite at once.

## Next steps

- Read the [architecture overview](https://example.com/arch)
- Pick up a `good-first-issue` ticket

# Research Summary: Remote Onboarding

## Key findings

1. **The first week matters most.** New hires who had a named buddy in week one
   were 2.3× more likely to rate onboarding as "good" or better.
2. **Documentation is the top complaint.** 61% of respondents said they couldn't
   find what they needed, especially:
   - how to request access to systems
   - who owns which service
   - where decisions are recorded
3. **Async-first teams onboard faster,** as long as decisions are written down.

## Method

We surveyed 214 employees who joined in the last 18 months and ran 15 follow-up
interviews. The survey questions are in the
[appendix](https://example.com/appendix). Interview notes were coded by two
researchers independently.

## What people said

> I spent my first three days just figuring out which Slack channels mattered.

> The best thing was a doc called "Start here." It had links to everything,
> and my buddy walked me through it on day one.

> > We should make that doc mandatory for every team.
>
> — reply from a team lead in the same interview

## Supporting data

| Onboarding practice | Teams using it | Avg. rating (1–5) |
|---|---:|---:|
| Named buddy | 58% | 4.1 |
| "Start here" doc | 34% | 4.3 |
| Scheduled 30/60/90 check-ins | 47% | 3.9 |
| None of the above | 12% | 2.6 |

## Related reading

- Smith & Lee, *Distributed Teams* (2024), chapter 3
- The internal wiki page on [onboarding checklists](https://example.com/checklists)
- https://example.com/research/onboarding-2026

## Recommendations

- Assign a buddy to every new hire, starting before day one
- Require a "Start here" doc for every team
- Record decisions in a searchable place, not only in chat

# Postmortem: Checkout Outage on October 9

**Severity:** SEV-1
**Duration:** 47 minutes (14:12–14:59 UTC)
**Impact:** ~18% of checkout attempts failed; estimated $42k in delayed orders

## Summary

A configuration change raised the payment service's connection pool from 50 to
500. The database hit its connection limit within minutes, and checkout requests
started timing out.

## Timeline (UTC)

| Time | Event |
|------|-------|
| 14:05 | Config change merged and deployed |
| 14:12 | Error rate alert fires for `payments-api` |
| 14:18 | On-call acknowledges, starts investigating |
| 14:31 | Database connection saturation identified |
| 14:44 | Config change reverted |
| 14:59 | Error rate back to baseline |

## Root cause

The pool size is set **per pod**, not per service. With 10 pods, the change
meant 5,000 potential connections against a database limit of 1,000.

```yaml
# payments-api/config.yaml (the bad change)
db:
  pool_size: 500   # was 50
```

## What went well

- Alerting fired within 7 minutes
- The revert path was fast and well understood

## What went poorly

- The change had no review from the database team
- The config file has no comment explaining that `pool_size` is per pod
- It took 13 minutes to connect the errors to the database

## Action items

| # | Action | Owner | Due |
|---|--------|-------|-----|
| 1 | Add a CI check that caps `pool_size × replicas` | Platform | Oct 23 |
| 2 | Comment `pool_size` semantics in the config | Payments | Oct 16 |
| 3 | Add a DB-connections panel to the payments dashboard | SRE | Oct 20 |
| 4 | Require DB-team review for pool changes | Eng leads | Oct 30 |

## Lessons

1. Per-instance settings need the multiplier spelled out next to them.
2. A dashboard panel for the shared resource would have cut diagnosis time:
   - connections in use
   - connections waiting
   - rejected connections

# Orders API Reference

Base URL: `https://api.example.com/v2`

All requests need an `Authorization: Bearer <token>` header.

## List orders

`GET /orders`

Returns orders for the authenticated account, newest first.

### Query parameters

| Name | Type | Required | Description |
|------|------|:--------:|-------------|
| `status` | string | No | One of `pending`, `paid`, `shipped`, `cancelled` |
| `limit` | integer | No | 1–100, default `20` |
| `cursor` | string | No | Pagination cursor from a previous response |

### Example

```bash
curl -H "Authorization: Bearer $TOKEN" \
  "https://api.example.com/v2/orders?status=paid&limit=2"
```

```json
{
  "data": [
    {"id": "ord_123", "status": "paid", "total": 4200},
    {"id": "ord_124", "status": "paid", "total": 1999}
  ],
  "next_cursor": "eyJpZCI6Im9yZF8xMjQifQ"
}
```

## Create an order

`POST /orders`

### Body

- `items` (array, required): each item has:
  - `sku` (string)
  - `quantity` (integer, ≥ 1)
- `shipping_address` (object, required)
- `coupon` (string, optional)

### Errors

| Code | Meaning |
|------|---------|
| `400` | Validation failed; see `errors[]` |
| `402` | Payment required |
| `409` | Duplicate `Idempotency-Key` |
| `429` | Rate limited; retry after the `Retry-After` header |

> **Idempotency:** send an `Idempotency-Key` header on every `POST`. Retrying with
> the same key returns the original response instead of creating a second order.

## Changelog

- **2026-09-01:** added `cursor` pagination; `page` is deprecated
- **2026-06-15:** `total` is now in minor units (cents)

# Study Notes: Distributed Consensus

## 1. The problem

A group of nodes must agree on a single value, even if some nodes crash or
messages are delayed. Consensus is the core of replicated logs, leader election,
and distributed locks.

## 2. Key properties

- **Safety**: nodes never decide different values
- **Liveness**: nodes eventually decide
- **Fault tolerance**: works with up to *f* failures out of *2f + 1* nodes

## 3. Raft in brief

1. **Leader election**
   - Every node starts as a *follower*
   - A follower that hears nothing for an election timeout becomes a *candidate*
     and asks for votes
   - A candidate with a majority becomes the *leader*
2. **Log replication**
   - The leader appends client commands to its log
   - It sends `AppendEntries` to followers
   - An entry is *committed* once a majority stores it
3. **Safety rule**
   - A candidate can only win if its log is at least as up to date as a majority's

## 4. Paxos vs. Raft

| | Paxos | Raft |
|---|---|---|
| Designed for | Correctness proofs | Understandability |
| Leader | Optional (Multi-Paxos uses one) | Always |
| Typical use | Spanner, Chubby | etcd, Consul |

## 5. Quick math

With *n* = 5 nodes, a majority is ⌊5/2⌋ + 1 = **3**, so the cluster survives
2 failures. With *n* = 4, a majority is still 3, so it survives only 1 failure,
which is why odd cluster sizes are preferred.

## 6. Questions to review

1. Why can't a node with a stale log become leader?
2. What happens to uncommitted entries when a leader crashes?
3. How does Raft handle a network partition that isolates the leader?

## 7. Sources

- Ongaro & Ousterhout, *In Search of an Understandable Consensus Algorithm* (2014)
- Lamport, *Paxos Made Simple* (2001)
- https://raft.github.io/

# fastqueue

A small, dependency-free job queue for Python services.

[![Build](https://img.shields.io/badge/build-passing-brightgreen)](https://example.com/ci)

## Features

- In-process or Redis-backed storage
- Retries with exponential backoff
- Scheduled jobs (`run_at=`)
- Type-annotated API

## Installation

```bash
pip install fastqueue
```

For Redis support:

```bash
pip install "fastqueue[redis]"
```

## Quick start

```python
from fastqueue import Queue

q = Queue()

@q.job(retries=3)
def send_email(to: str, subject: str) -> None:
    ...

send_email.delay("user@example.com", "Welcome!")
q.run_worker()
```

## Configuration

| Option | Default | Description |
|--------|---------|-------------|
| `backend` | `"memory"` | `"memory"` or `"redis"` |
| `redis_url` | `None` | Required when `backend="redis"` |
| `max_retries` | `5` | Upper bound for any job |
| `poll_interval` | `0.5` | Seconds between polls |

## Usage notes

1. Jobs must be importable by the worker process.
2. Arguments must be JSON-serializable.
3. Use `q.job(timeout=...)` for long-running work:
   ```python
   @q.job(timeout=300)
   def rebuild_index(): ...
   ```
4. Call `q.shutdown()` on exit to flush pending acks.

> **Note:** the in-memory backend loses jobs when the process exits. Use Redis
> in production.

## Contributing

PRs are welcome. Please run `make test` and `make lint` before opening one, and
see [CONTRIBUTING.md](https://example.com/contributing) for details.

MIT © 2026 fastqueue contributors

# How to Set Up a Local Development Environment

This guide walks you through setting up the service on macOS or Linux. It takes
about 15 minutes.

## Prerequisites

- Python 3.12 or newer
- Docker Desktop (or Docker Engine on Linux)
- Access to the team's GitHub organization

## Steps

1. **Clone the repository.**

   ```bash
   git clone https://github.com/example/service.git
   cd service
   ```

2. **Create a virtual environment and install dependencies.**

   ```bash
   python3 -m venv .venv
   source .venv/bin/activate
   pip install -r requirements-dev.txt
   ```

3. **Start the backing services.** This starts Postgres and Redis in containers:

   ```bash
   docker compose up -d db redis
   ```

   Wait until both containers report `healthy`:

   ```bash
   docker compose ps
   ```

4. **Configure your environment.**
   - Copy `.env.example` to `.env`
   - Set `DATABASE_URL` to `postgresql://dev:dev@localhost:5432/service`
   - Leave `FEATURE_FLAGS` empty unless you need a specific flag

5. **Run the migrations and start the server.**

   ```bash
   make migrate
   make run
   ```

   The server listens on <http://localhost:8000>.

## Troubleshooting

**Port 5432 is already in use.** Another Postgres is running. Stop it, or change
the port mapping in `docker-compose.yml`.

**`pip install` fails on `psycopg`.** Install the Postgres client headers:

- macOS: `brew install libpq`
- Debian/Ubuntu: `sudo apt install libpq-dev`

> **Tip:** run `make doctor` to check every prerequisite at once.

## Next steps

- Read the [architecture overview](https://example.com/arch)
- Pick up a `good-first-issue` ticket

# Postmortem: Checkout Outage on October 9

**Severity:** SEV-1
**Duration:** 47 minutes (14:12–14:59 UTC)
**Impact:** ~18% of checkout attempts failed; estimated $42k in delayed orders

## Summary

A configuration change raised the payment service's connection pool from 50 to
500. The database hit its connection limit within minutes, and checkout requests
started timing out.

## Timeline (UTC)

| Time | Event |
|------|-------|
| 14:05 | Config change merged and deployed |
| 14:12 | Error rate alert fires for `payments-api` |
| 14:18 | On-call acknowledges, starts investigating |
| 14:31 | Database connection saturation identified |
| 14:44 | Config change reverted |
| 14:59 | Error rate back to baseline |

## Root cause

The pool size is set **per pod**, not per service. With 10 pods, the change
meant 5,000 potential connections against a database limit of 1,000.

```yaml
# payments-api/config.yaml (the bad change)
db:
  pool_size: 500   # was 50
```

## What went well

- Alerting fired within 7 minutes
- The revert path was fast and well understood

## What went poorly

- The change had no review from the database team
- The config file has no comment explaining that `pool_size` is per pod
- It took 13 minutes to connect the errors to the database

## Action items

| # | Action | Owner | Due |
|---|--------|-------|-----|
| 1 | Add a CI check that caps `pool_size × replicas` | Platform | Oct 23 |
| 2 | Comment `pool_size` semantics in the config | Payments | Oct 16 |
| 3 | Add a DB-connections panel to the payments dashboard | SRE | Oct 20 |
| 4 | Require DB-team review for pool changes | Eng leads | Oct 30 |

## Lessons

1. Per-instance settings need the multiplier spelled out next to them.
2. A dashboard panel for the shared resource would have cut diagnosis time:
   - connections in use
   - connections waiting
   - rejected connections

# Study Notes: Distributed Consensus

## 1. The problem

A group of nodes must agree on a single value, even if some nodes crash or
messages are delayed. Consensus is the core of replicated logs, leader election,
and distributed locks.

## 2. Key properties

- **Safety**: nodes never decide different values
- **Liveness**: nodes eventually decide
- **Fault tolerance**: works with up to *f* failures out of *2f + 1* nodes

## 3. Raft in brief

1. **Leader election**
   - Every node starts as a *follower*
   - A follower that hears nothing for an election timeout becomes a *candidate*
     and asks for votes
   - A candidate with a majority becomes the *leader*
2. **Log replication**
   - The leader appends client commands to its log
   - It sends `AppendEntries` to followers
   - An entry is *committed* once a majority stores it
3. **Safety rule**
   - A candidate can only win if its log is at least as up to date as a majority's

## 4. Paxos vs. Raft

| | Paxos | Raft |
|---|---|---|
| Designed for | Correctness proofs | Understandability |
| Leader | Optional (Multi-Paxos uses one) | Always |
| Typical use | Spanner, Chubby | etcd, Consul |

## 5. Quick math

With *n* = 5 nodes, a majority is ⌊5/2⌋ + 1 = **3**, so the cluster survives
2 failures. With *n* = 4, a majority is still 3, so it survives only 1 failure,
which is why odd cluster sizes are preferred.

## 6. Questions to review

1. Why can't a node with a stale log become leader?
2. What happens to uncommitted entries when a leader crashes?
3. How does Raft handle a network partition that isolates the leader?

## 7. Sources

- Ongaro & Ousterhout, *In Search of an Understandable Consensus Algorithm* (2014)
- Lamport, *Paxos Made Simple* (2001)
- https://raft.github.io/
