## Run history / incidents

- **Playwright browser wasn't authenticated to Google at pass start.** Every one of the 8 parallel shards independently hit the sign-in redirect within its first few `**Playwright: required**` TCs, concluded Playwright was unusable, and fell back to API-level-only verification for its entire remaining run. The user authenticated Playwright mid-pass; corrections were sent to the two still-running shards (Sheets, Docs-content retries) — one was misdirected due to an agent-ID mix-up on Aziz's own end (caught and corrected). A dedicated re-verification pass then redid the ~17 highest-value already-completed visual checks (10 docs/drive_transfer TCs, 7 Sheets TCs) with real screenshots — all PASS, zero discrepancies from the API-only evidence. Filed **PR #686** to make Playwright-auth verification (a real navigate, not just a connection check) a mandatory pre-flight step for future passes, done once centrally before spawning shards.
- **Service account wasn't subscribed to the fixture calendar.** The Calendar shard's reads against `{CALENDAR_ID}`/`{EVENT_ID}` all 404'd on the SA prefix; it ran its full 77-TC suite against two SA-owned scratch calendars instead (valid tool-behavior coverage, but not against the real fixture). A targeted OAuth re-run against the real fixture closed the gap for 6 identity-sensitive TCs (CAL05/16/60/62/67) plus 2 that only work under OAuth at all (CAL17/22 — attendee invites, which a service account cannot send) — all PASS, real fixture confirmed untouched (`updated` timestamp identical pre/post).
- **Cross-shard fixture interference (transient, resolved).** The Sheets shard's writes to `{SPREADSHEET_ID}` were caught mid-mutation by the Drive-transfer shard's CSV-export comparison (TC-D86 vs TC-D104 diverged: extra column, an `#ERROR!` cell, an extra row). Re-checked after the Sheets shard restored the fixture to seed state — both exports now agree byte-for-byte. Not a product bug; a sharding-design lesson (two shards touching the same fixture, one read-mostly, without wave-sequencing).
- **Main-checkout OAuth `token.json` refresh token is failing (`invalid_grant`) for fresh processes.** Already-running MCP server processes are unaffected (they hold an already-refreshed in-memory token — confirmed live-working throughout this pass), but any *new* script/session using this file will hit it and fall into an interactive-consent hang. This blocked one live re-verification (TC-DOC159 — raw `documents().get()` read of blockquote indent/border), disposed instead via a source-diff argument (the exact code path hasn't changed since its last live PASS). Recommend re-running `scripts/oauth_setup.py` before the next session needs a fresh OAuth connection — flagged to the user, not a QA finding.
- **Two subagent-prompt mistakes, both self-inflicted and non-blocking:** the TC-I24/TC-I02 concurrency subagents were given a slightly wrong tool-call syntax (`range="Sheet!A1:C3"` instead of separate `sheet=`/`range=` params) for their first 1-2 iterations each; all subagents self-corrected immediately and the remaining iterations are the ones adjudicated. Neither is a transport/locking signature — genuine client-side parameter errors.
- **Google Drive API had two transient server-side blips** (an `export_file` `HttpError 500 Internal Error`, and one `delete_file(permanent=True)` `404` on a file `get_file_metadata` could see and trash could act on — isolated to the service-account prefix specifically; the same delete succeeded immediately via OAuth on the identical file, suggesting a Shared-Drive Content-Manager-role permission-model quirk rather than a code defect). Neither reproduced on retry via the correct auth path; not filed as product bugs.

**BUG-SS draft:**
> **Title:** `share_spreadsheet` fails with "File not found" on any Shared Drive file — missing `supportsAllDrives=True`
> **Body:** `tools/drive/sharing.py`'s `share_spreadsheet._share_one` calls `drive_service.permissions().create(fileId=spreadsheet_id, ...)` with no `supportsAllDrives=True` — the only permission-mutating call in the file missing it (`update_permission`, `remove_permission`, `list_permissions`, `transfer_ownership`, and `share_file._share_one` all pass it). On a Shared Drive item, the Drive API returns "File not found" for a `permissions().create()` call that omits this flag, so `share_spreadsheet` fails on any file in a Shared-Drive deployment — which, post-#305, is now this project's own QA fixture environment. `share_file` (a separate tool, same underlying operation) works correctly and is a functional workaround in the meantime. Fix: add `supportsAllDrives=True` to the one call site, mirroring its siblings. Found during the v0.9.0 QA pass (TC-D18/19/20/23/24/D176).
> **Labels:** bug, v0.9.0

**BUG-CACHE draft:**
> **Title:** `list_files`/`list_spreadsheets`/`list_folders` — folder-listing cache key omits `max_results`, causing silent truncation and cache poisoning
> **Body:** The folder-listing cache (shared by `list_files`, and transitively `list_spreadsheets`/`list_folders`) keys its cached entries without `max_results` as part of the key. Two live-reproduced consequences: (1) a call with a smaller `max_results` than a prior cached call for the same folder gets served the prior (larger, unfiltered) cached result and *ignores* its own limit — e.g. `list_files(FOLDER_ID, max_results=2)` returned 5 items because an earlier default-size call had already cached 5; (2) conversely, a small-`max_results` call that misses cache and fetches fresh then *stores* its own truncated result under the same key, so a later default-size call for the same folder gets the truncated list back until an explicit `refresh_cache()`. Both reproduced twice on a fresh fetch/cache cycle. Expected: `max_results` (or an equivalent "no limit was ever specified vs. explicit limit" signal) should be part of the cache key, or the cap should be applied to the full cached list after retrieval rather than baked into what gets cached. Found during the v0.9.0 QA pass (TC-D38/D40).
> **Labels:** bug, v0.9.0

**BUG-LF draft:**
> **Title:** `list_folders` with no parent ignores `DRIVE_FOLDER_ID`, hardcodes personal My-Drive root
> **Body:** `tools/drive/files.py` `list_folders(parent_folder_id=None)` appends `q += " and 'root' in parents"` unconditionally when no parent is given — unlike `create_folder`/`create_spreadsheet`, which resolve a missing parent from `lc.folder_id` (= `DRIVE_FOLDER_ID`). On a Shared-Drive deployment (`DRIVE_FOLDER_ID` set) `list_folders(None)` therefore lists the OAuth user's *personal* My-Drive root, not the configured default; for a pure service-account deployment there is no personal root at all, so it returns nothing. Expected: fall back to `lc.folder_id` when set, mirroring `create_folder`. Surfaced by #680 / v0.9.0 QA pass (TC-D27, confirmed live — returned `{"result": []}` on the Shared-Drive OAuth deployment). Docstring also says "lists folders from 'My Drive' root" with no mention of the fallback.
> **Labels:** bug, v0.9.1

**BUG-DF draft:**
> **Title:** `download_file` with a non-existent trailing-slash directory creates a clobbering file instead of the directory
> **Body:** `download_file(file_id, local_path="/some/new/dir/", ...)` where `/some/new/dir/` doesn't exist yet creates a plain *file* at that literal path (not a directory containing the downloaded file), and reports `local_path` as if it had saved the file inside a directory. Every subsequent download to the same `local_path` silently overwrites that file with no warning. Once the directory already exists, all directory-target behavior is correct. Expected: create the directory (`mkdir -p`-style) when `local_path` ends in a path separator and doesn't exist, or raise a clear error rather than silently writing a file where a directory was implied. Found during the v0.9.0 QA pass (`drive_transfer.md`).
> **Labels:** bug, v0.9.1
