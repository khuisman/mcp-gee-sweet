    List Start Numbers¶

    Date: 2026-11-03. Issue: #1118.

    3. a produces <ol start="3">, and the Doc numbered it 1, 2. This doc records what the API allows and why the fix has two mechanisms.

    What the API allows (checked live, 2026-11-03)¶

    Attempt Result
    A request that writes NestingLevel.startNumber None exists in the batchUpdate request list (discovery revision 20261028)
    A numbered preset with an offset None in createParagraphBullets' bulletPreset enum
    Create throwaway items, then delete them Rejected: the rest renumber, startNumber stays 1
    Drive import of <ol start="3"> Sets startNumber 3, with glyphType unspecified and a 30/12pt indent
    Text inserted inside an imported list Stays in that list, and the list keeps its start after the original items are deleted
    createParagraphBullets right after an imported list Does not join it: a new list at 1
    files.update with HTML over an existing Doc Works, but removes the headers, resets named styles and margins

    Decision¶

    1. Continue the last list where that's the right number. Docs numbers a list by listId, past anything between its items (#1094). A top-level list that counts up from where the last top-level list stopped, in the same quote, is bulleted with it, and the blocks between are taken back out. That fixes LX-09 with a real list. Two lists in a row with different markers (1. a, 2) b) are covered too, since the second starts where the first stopped.

    Sharing a listId changes how the Doc reads back, so a block that _ListItemContext can't tell from one inside the item stops it: a table, an empty paragraph, a quote two or more levels deep. Without that, 1. a, a table, 2. b exported the table under 1., and a rewrite from the export moved it. So does any other list between them, a nested one included. 2. Otherwise write the numbers as text. The item becomes <number>.<tab><text> at the list level's hanging indent. The tab stops at indentStart, so a literal list lines up with a real one (compared in a PDF render) while its marker fits the 18pt gap. Past that the tab would run to the next default stop, 36pt on, leaving the wrapped lines behind, so a wider marker starts further left (_literal_item_gap, from an Arial estimate at the default sizes). indentStart stays at the level's text indent, where the blocks and sublists under the item already sit. A nested one uses its level's glyph, since a real sublist there shows letters or roman numerals. This keeps the numbers right at every entry point, in new and existing Docs alike, at the cost of not being a Docs list. The maintainer chose this over the alternatives below.

    Rejected¶

    • Seeding a list through Drive's import. It only works for a new Doc, because over an existing one it destroys the Doc's styles, so write_doc_content and update_doc_from_file would still show the wrong numbers. Every other step would have to change too: seeds must sit where each list goes, and text would be inserted into them rather than bulleted, with a different indent and glyph.
    • Leaving it as a known limitation. LM-04 would keep failing, on the ticket's own done-when.
    • Keeping throwaway items, hidden. They'd show up in exports and in get_doc_as_markdown.

    Read side¶

    doc_to_ast._literal_marker turns a stand-in back into a BulletItem, so the export says 3. Three rather than the escaped 3\. a paragraph would get. It needs the whole signature: no bullet, the hanging indent, and the marker that level writes. A quoted stand-in's indent adds its list level to its quote depth, and nothing in the Doc separates them. So a quoted stand-in reads as an item only at level 0 with a digit marker, and a nested one exports as a plain paragraph. That's the maintainer's scope cut after three attempts that each moved the failure (PR #1368): level 0 always, the shallowest level writing the marker (a roman numeral is letters too, so iii. read as 6327), and the open list's quote depth (the stand-in can have a quote its list doesn't). Don't try to recover its level. The Doc itself renders correctly either way. The anchor pass uses the same check, so a heading numbered by hand keeps its number.

    A leading tab in a block inside the bullet range is consumed like a depth-tab. _top_list_requests puts it back right after that block's deleteParagraphBullets, so nothing past the list sees it gone. Every position it computes before that allows for it (block_tabs_before). That also fixes the same defect in a block inside a list item, which predates this work.

    A block loose in an <ol> (<ol><li>a</li><p>x</p><li>b</li></ol>) used to end its Docs list, so b showed 1. It now joins the list again, the same way, and so a later list's count holds. A quote separator between two nodes in one list carries the shallower one's item for the same reason.

    <ol reversed> and <li value> give numbers a Docs list can't show either, so html_parser numbers a list's items at the end of the parse, as a browser would, and a list that comes out 1, 2, 3 has no numbers at all.

    An AST from document_to_ast never reaches the emitter with list_path set, so _resolve_list_starts leaves its numbered items alone.
